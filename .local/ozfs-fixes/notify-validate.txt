NOTIFY / SIGCHLD-lost-wakeup FIX -- ACCEPTANCE VALIDATION (pasted evidence)
================================================================================
Base 401852c67 (integ/pg-fork-zfs tip, has fix#1).  Fresh-8k-pool harness.
Two fixes, both #if CONF_fork:
  (A) libc/signal.cc kill(): signal-selective self-signal AS routing --
      else if (pid == getpid() && (sig == SIGURG || sig == SIGUSR1))
          target_as = osv::fork::as_for_pid(pid);
      (SIGURG latch + SIGUSR1 ProcSignalBarrier route to the caller's own COW
       AS; the child-exit SIGCHLD kill(getpid(),SIGCHLD) is NOT diverted -> its
       reaper runs in AS0, so the postmaster reaps the startup process and boots.)
  (B) libc/pipe.cc pipe2(): pipe_buffer + pipe_file on the identity kernel heap
      (fork_arena::kernel_heap_scope) so the latch self-pipe is coherent across
      every fork AS (cross-backend SetLatch->SIGURG->sendSelfPipeByte writes the
      SAME pipe the waiting backend epoll-polls).

ROOT CAUSE (proven by instrumentation, see notify-root.txt): the lost
notification is the child-exit -> parent SIGCHLD.  PostgreSQL's startup process
(a fork child) finishes recovery and exits; OSv fork emulation
(fork.cc child_exited -> kill(getpid(), SIGCHLD)) synthesizes the parent
notify.  The broad K1 (else if pid==getpid() -> current AS) diverted that
SIGCHLD reaper into the child's DYING COW AS, where it faults at the mmap slot
(0x2000..) and nests -> the postmaster never reaps -> never reaches "ready" ->
forked backends wait forever in epoll on their latch pipes.  Restricting the
routing to SIGURG/SIGUSR1 keeps the SIGCHLD reaper in AS0 (correct) while still
enabling the DROP DATABASE self-signal.
