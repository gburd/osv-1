W1 (mmap populate spin) -- REAL OSv MM FIX (not the sysv workaround):
  root cause: populate::page() returned true even when a page provider's level-1 (2M) map()
  returned false to force 4K; the walker then left the 2M PTE empty -> instruction re-faulted
  forever at 99.9% CPU the moment PG first touched shared_buffers (default shared_memory_type=mmap).
  fix: return false at a large-capable level so the walker descends to the 4K map(). PG now uses
  its DEFAULT mmap shared memory; NO sysv config needed.

W2 (catalog-read-zero across forked backends) -- root cause + already-committed fix:
  the zero page was PG's shared_buffers catalog page read in a forked backend from a non-coherent
  shared segment. Already solved by the committed shared_anon_page_provider (8bec67d1c): a global
  VA-keyed registry maps a given shared-anon page VA to the SAME physical frame in every fork AS.
  The W1<->W2 crux: the sysv workaround routed shm through SysV shm (a DIFFERENT OSv path the
  provider does NOT cover), so sysv dodged W1 but re-opened W2. Fixing W1 puts PG back on the
  default mmap path, which IS coherent -> W2 solved with no new code.

W3 (page_range_allocator::remove in l2::fill_thread) -- DOWNSTREAM OF W1, GONE:
  did not reproduce once W1 was fixed; it was the L2 pool churn caused by the 2M populate spin.
