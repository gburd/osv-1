*** FINDING 0 (BLOCKER, and it explains the whole "#1467 never measured" saga): ***
#1467 batch-wakeup AS WRITTEN CRASHES under real TCP load on SMP.
  BATCH=1 (OSV_NET_BATCH_WAKE=1, default): boots, PG "ready to accept", then on the
    FIRST real TCP connection the guest faults:
      Assertion failed: sched::preemptable() (arch/x64/mmu.cc: page_fault: 38)
      [backtrace] page_fault <- ... <- tcp_input <- netisr_dispatch_src
                  <- virtio::net::receiver()+842
  BATCH=0 (per-packet, byte-identical to upstream path): boots + SERVES cleanly.
    psql select 1 -> 1 ; inet_server_addr = 192.168.100.2 (REAL tap NIC, not loopback).

ROOT CAUSE (drivers/virtio-net.cc net::receiver, batch path):
  The batch path holds osv::rcu_read_lock across the ENTIRE drain loop INCLUDING the
  slow path `(*_ifn->if_input)(_ifn, m_head)` (the non-fast-path packets go up the full
  BSD stack: netisr_dispatch_src -> ip_input -> tcp_input). rcu_read_lock disables
  preemption. tcp_input (and the stack it calls) can demand-fault a lazily-mapped page;
  page_fault asserts sched::preemptable() -> abort.
  The ORIGINAL per-packet path takes rcu_read_lock INSIDE classifier::post_packet() and
  RELEASES it before returning, so the if_input slow path runs preemptable. #1467 widened
  the lock scope over if_input and broke that invariant.

  => This is the real reason every prior attempt to measure #1467's SMP payoff "wedged":
     it was not an environmental wedge, it is #1467 crashing the guest on TCP under SMP.
     #1467 CANNOT be landed or measured as-is. It needs a fix (below).

*** FIX FOR #1467 (commit c1b921f49 on roceil-substrate, drivers/virtio-net.cc): ***
Defer slow-path (non-classified) RX packets past the batch-wake rcu_read_lock.
  - Collect non-fast-path mbufs into a std::vector<mbuf*> during the drain.
  - Run them through (*_ifn->if_input)() AFTER wake_batch.flush()+rcu_read_lock.unlock(),
    where the receiver thread is preemptable again.
  - Fast-path (net_channel) packets unaffected; the IPI-coalescing batch win preserved.
VALIDATED: BATCH=1 (fixed loader) boots, serves (select 1 -> 1), survives c16 RO
  (24717 tps, 0 failed) - the exact concurrency that crashed pre-fix. NO preemptable assert.
=> This is the missing piece that made #1467 unmeasurable. #1467 needs THIS fix folded in.

*** ROOT CAUSE NAMED (full backtrace, all 32 backends identical): ***
================================================================================
The RO c8 ceiling / post-c8 collapse is a SINGLE GLOBAL MUTEX in the fork-coherent
shared-anon page provider. Every PG backend page-fault on shared_buffers serializes here:

  lockfree::mutex::lock  (this=0x600105e47a00  <- SAME lock addr for ALL backends)  lfmutex.cc:129
   <- mmu::shared_anon_page_provider::shared_page   core/mmu.cc:1910  WITH_LOCK(reg->lock)
   <- mmu::shared_anon_page_provider::map           core/mmu.cc:1940
   <- mmu::populate::page                           core/mmu.cc:1274  (demand-fault shared_buffers)
   <- mmu::map_range ... (page fault on the 8GB MAP_SHARED anon segment)

STRUCTURE (core/mmu.cc:1869): shared_anon_registry = { mutex lock; std::unordered_map<VA,page> }
  ONE global lock + ONE map for the whole process. Every fault on any shared_buffers page,
  from any of the 32 backends, takes reg->lock even for the fast-path find(). Under
  concurrency all backends serialize on this one lock -> tps = concurrency/latency, ~99.9%
  idle (backends BLOCKED on the mutex, not spinning, not CPU-bound).

EVIDENCE:
  - gdb osv info threads (c32, load running): 32 pgbench backends ALL "waiting" at
    core/lfmutex.cc:129 (lockfree::mutex::lock slow path), crammed onto cpu0/1/2.
  - all 4 sampled backend backtraces IDENTICAL: blocked on lock 0x600105e47a00 in
    shared_anon_page_provider::shared_page.
  - sampler: 99.9% idle (they block, don't spin).
  - tps=c/latency holds exactly; latency grows with c (serialized resource).

WHY IT PINS AT c8 REGARDLESS OF vCPU COUNT (8/32/48):
  The lock is global; contention on it does not scale with cores. ~8 concurrent faulters
  saturate the lock's throughput (acquire/release + the alloc/find under it); beyond that
  they queue and latency climbs linearly -> knee at ~c8 on any core count. Adding vCPUs
  just adds idle CPUs (nothing to run - everyone's blocked on the one lock).

WHY #1467 BATCH-WAKEUP DOES NOT LIFT IT (measured, below): the ceiling is a shared-memory
  page-fault mutex, NOT the net RX wake path. Coalescing wake IPIs cannot help a workload
  serialized on a mmu lock. (#1467 is still a valid net optimization + its preemptable bug
  is a real fix, but it is not THIS bottleneck.)

This is CONF_fork-specific (shared_anon_page_provider exists only for the PG fork stack).
