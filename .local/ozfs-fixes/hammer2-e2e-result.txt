TWO NEW FAULTS surfaced (both the KNOWN fork-COW-arena coherence class, NEITHER is the

NEW FAULT A - forked-backend AS teardown NULL-deref in the reaper (post-schema-build COMMIT storm)
  addr 0x0; RDI=0x300003e87560 (fork COW arena base 0x3000..).
  RIP mmu::destroy_address_space (core/mmu.cc:767 = `as->owned_vmas->clear_and_dispose([](vma*v){delete v;})`)
    <- fork.cc:621 child->set_cleanup lambda (destroy child_as)
    <- sched::thread::reaper (core/sched.cc:2086) <- thread::main
  Mechanism (hypothesis, matches the fork-arena class): the child AS's owned_vmas snapshot (or a file_vma's
  page_allocator/fileref) lives in / points into the recycled COW fork arena; ~vma dereferences a stale/NULL
  arena pointer when the reaper tears down a short-lived forked backend under heavy connection churn.
  Trigger phase: end of 20wh schema build, HammerDB's autocommit COMMIT storm reaping many backends fast.

NEW FAULT B - forked-backend dlopen get_library corruption (stored-proc first-call, no preload)
  addr 0xfffffffffffff000; RBX/RDI/R8/R9/R12-R15 all 0x30000021c9.. (fork COW arena).
  RIP elf::program::get_library (core/elf.cc:1646) <- dlopen (libc/dlfcn.cc:49) <- app (0x100000b1b1e9)
    (return addr 0x692f383167702f6b = ASCII "k/pg81g/i" = a corrupted/overwritten stack return -> arena node walk
     over COW-incoherent list).
  Mechanism (hypothesis): a forked backend calls dlopen (plpgsql.so on first stored-procedure call); the linker's
  library/module list nodes it walks live in the COW fork arena and are incoherent across the fork boundary.
  WORKAROUND that made the NOPM run clean: ALTER SYSTEM SET shared_preload_libraries='plpgsql' + restart, so the
  postmaster dlopens plpgsql in AS0 BEFORE any fork; forked backends inherit it and never dlopen-in-fork.
  => real residual: dlopen-in-a-forked-child is not fork-coherent (get_library list on the arena). Same class as
     the shipped fixes (route the linker list/nodes to the identity kernel heap under CONF_fork).
