7. TIMER-FIRING ANSWER (the decisive lead resolved) -- it is option (b)
================================================================================
The guest clock and timer IRQ are ALIVE at the wedge. Sampling cpu1's
park_wakeup_timer at ~4s wall intervals during the hang:
   sample0  armed @ 30.101s
   sample1  armed @ 34.104s   (+4.0s)
   sample2  armed @ 38.107s   (+4.0s)
=> park_wakeup_timer FIRES and RE-ARMS every few seconds. park_timer_fired() IS
   running in the timer IRQ. (cpu2 pwt stuck armed@60.9s; cpu0 free.)

So it is NOT a stopped clock / dead timer IRQ (rules out option a). It is
option (b): the timer fires, park_timer_fired() calls wake_with_irq_disabled()
on the due parked forked backend and bumps its _parked_deadline to max, BUT the
woken backend NEVER RUNS -- the wake is LOST. All CPUs stay idle,
incoming_wakeups_mask=0, the backend stays status=waiting.

ROOT (for the fix): the wake of a PARKED, cross-AS (COW-child) forked backend
issued from park_timer_fired() in timer-IRQ context (wake_with_irq_disabled ->
wake_impl: CAS waiting->waking, enqueue on tcpu->incoming_wakeups, set mask,
need_reschedule/IPI) does not result in the thread being run. Candidate
mechanisms to check next:
  * wake_impl runs in the timer IRQ under whatever AS the cpu holds; the enqueue
    touches tcpu->incoming_wakeups (identity) + the thread's _wakeup_link
    (in the thread object, identity) -- should be AS-safe, but verify the
    detached_state CAS and _wakeup_link are not in COW memory.
  * the woken thread is enqueued but on switch-in unpark_timers()/resume_timers()
    or the fork park state (_timers_parked still true) drops it, or
    handle_incoming_wakeups skips it.
  * park_timer_fired bumps _parked_deadline=max BEFORE the wake is guaranteed
    delivered; if the wake CAS races the thread's own re-park, it is lost.
Confirm by watching one backend's detached_state.st and _parked_deadline across
two park_timer_fired cycles: if st goes waiting->waking but never queued->running,
the loss is in the wake->enqueue->switch-in handshake for a parked cross-AS thread.

8. FINAL PRECISION -- the wake is NOT lost in the scheduler; the EVENT is missing
================================================================================
Watched both backends' detached_state.st + _parked_deadline across 5 park cycles
(~3s apart) at the wedge:
  tid 598: st=waiting parked=true deadline=300.788s  (CONSTANT -- never advances)
  tid 599: st=waiting parked=true deadline=30.06 -> 33.06 -> 36.07 -> 39.07 -> 42.07s
           (advances ~+3s each cycle, tracking `now`)
  incoming_wakeups_mask = [0,0,0,0] at every sample.

Interpretation:
  * park_timer_fired() does NOT set 599's deadline to max; instead 599's deadline
    is recomputed fresh (= now + its WaitLatch timeout) each cycle. => 599 IS
    being woken + switched in, runs briefly, finds NO epoll event, re-arms its
    timeout timer and re-blocks (re-parked with a new earliest_active_deadline).
    It loops on its own WaitLatch timeout making ZERO progress.
  * 598 sits with a fixed far-future deadline (300s): it is waiting for an EVENT
    (not a short timeout) that never arrives.
=> The scheduler wake path is NOT dropping wakeups. The forked backend(s) are
   waiting on an inter-process EVENT (a latch set / socket-ready / pipe write
   from the postmaster or a sibling backend) that is NEVER DELIVERED across the
   fork COW boundary during startup. PG startup handshake deadlocks: the process
   that should SetLatch/write-the-pipe to advance startup either never runs or
   its write lands in the wrong AS's copy of the fd/latch state.

This reframes the ROOT away from the scheduler timer/wake path (which is healthy:
clock advances, park timer fires, short-timeout waiter re-runs) and back toward
the FORK COW COHERENCE of the latch/epoll self-pipe / cross-process fd state --
the same family as the DROP DATABASE self-signal issue, but at startup. The
missing wakeup is an inter-backend latch/pipe notification not crossing the COW
AS boundary; find which fd/latch write is not seen by the waiting backend's AS.
NEXT: identify WHICH PG process should wake 598 and WHY its notification (self-
pipe write / socket / SetLatch shared-memory flag) is invisible in 598's COW AS.
The layout (K1) sensitivity is because the fork/first-switch ordering vs the
postmaster's startup signals shifts, changing whether the notification races
ahead of or behind the child establishing its COW mapping of the shared latch.
