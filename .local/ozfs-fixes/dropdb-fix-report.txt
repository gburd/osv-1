1. THE FIX (what / where / why boot-safe / why conf_fork=0 identical)
--------------------------------------------------------------------------------
WHERE: libc/signal.cc, kill(), inside #if CONF_fork.

WHAT: the fork-aware kill() routed a CROSS-backend signal to the target's AS via
  as_for_pid(pid) but EXCLUDED the self case (pid == getpid()), leaving
  target_as = nullptr so a self-signal handler ran in AS0 (kernel AS), not the
  caller backend's own COW AS. New branch:

    } else if (pid == getpid()) {
        target_as = mmu::current_address_space();
        if (target_as == mmu::kernel_address_space()) {
            target_as = nullptr;   // top-level app / kernel: AS0, as before
        }
    }

  Downstream (unchanged) code then runs the handler thread in target_as, and
  uses that AS's private signal table.

WHY it fixes DROP DATABASE (matches ckpt-diag.txt exactly):
  EmitProcSignalBarrier() does kill(pid, SIGUSR1) to EVERY backend slot INCLUDING
  the emitter's own; WaitForProcSignalBarrier() then blocks until every slot
  (its own included) advances pss_barrierGeneration. A backend advances its own
  generation only from ProcessProcSignalBarrier() run by CHECK_FOR_INTERRUPTS()
  when ProcSignalBarrierPending is set -- and that flag is set by the SIGUSR1
  handler (HandleProcSignalBarrierInterrupt). ProcSignalBarrierPending /
  InterruptPending are process-global `volatile sig_atomic_t`, i.e. the backend's
  COW-private copy in its own AS. With the handler in AS0 it set them in AS0's
  copy; the emitting backend never saw ProcSignalBarrierPending, never absorbed
  its own barrier, and WaitForProcSignalBarrier waited for its own PID forever
  ("still waiting for backend with PID N", N == self). Running the handler in the
  caller's own COW AS sets the flag in the copy the backend actually reads.

WHY boot-safe: current_address_space() is cheap and side-effect free -- it is
  sched::thread::current()->address_space() with a kernel_as fallback, NO lock,
  NO fault, NO re-entry into as_for_pid. Empirically the branch NEVER fires
  during PG startup: an instrumented build (debugf on entry to the branch)
  printed ZERO [SELFSIG] lines across every boot, whether the boot reached PG or
  wedged. EmitProcSignalBarrier is only called by DROP DATABASE and
  DROP/CREATE TABLESPACE (dbcommands.c, tablespace.c) -- never at startup.

WHY conf_fork=0 identical: the entire new logic is inside the #if CONF_fork
  block. The #else (non-fork) path is textually unchanged, so a conf_fork=0
  object is byte-identical. For the top-level app / postmaster (getpid()==OSV_PID,
  current AS == kernel_as) the branch resets target_as to nullptr -> AS0 handler,
  identical to today.

2. THE WIP's "startup hang" -- WHAT IT REALLY WAS, AND HOW I AVOIDED IT
--------------------------------------------------------------------------------
The WIP (dropdb-wip.patch) was the SAME AS-routing change plus a debugf. It was
reported to "hang startup". I reproduced it, and then reproduced the SAME
crash/hang with PURE HEAD (signal.cc reverted to c8f9c82b, no change at all):

  * The instrumented WIP printed ZERO [SELFSIG] lines before the wedge -> the new
    branch is not even reached during startup.
  * Pure HEAD crashes/hangs at the identical point (right after the
    end-of-recovery checkpoint, before "ready to accept").

So the startup failure is NOT the signal.cc change. The only real risk the WIP
carried was using an AS accessor that might lock/fault on the hot self-kill path;
I avoided that by using mmu::current_address_space() (lock-free, fault-free,
verified in core/mmu.cc:229) and by dropping the debugf. The committed fix
changes behavior ONLY for a fork-child self-signal whose current AS is a child
COW AS; AS0 / non-fork / conf_fork=0 are unchanged.

3. WHY VALIDATION IS BLOCKED: two pre-existing startup bugs (both in PURE HEAD)
--------------------------------------------------------------------------------
Method: fresh reseed of the pgdata pool (clean initdb via cpiod, clean export),
then boot loops at -smp1/-smp4/-smp8, hp=off. Also isolated a single-disk pool.

BUG A -- ZFS mount SEGV (raidz path), now ~deterministic
  Boot -> import OK ("Pool 'pgdata' is up-to-date", ONLINE, no errors, read-only
  `zfs get` works) -> `zfs mount pgdata` faults:
     Aborted
     handle_mmap_fault (libc/signal.cc:241)
     mmu::vm_fault (core/mmu.cc:2318 == vm_sigsegv)
     page_fault
     ...zfs.so...  (zfs_mount -> zfs_mount_at -> sys_mount)
     sys_mount (fs/vfs/vfs_mount.cc:195 == the VFS_MOUNT call into ZFS)
  A wild-pointer SIGSEGV inside the ZFS VFS_MOUNT op. 8/8 raidz boots failed here
  on a freshly-seeded, healthy pool. A SINGLE-DISK pgdata pool does NOT hit this
  (mount succeeds, PG starts) -- so it is specific to the raidz1+log+cache mount
  path, not the signal fix.

BUG B -- PG-startup allocator-recursion wedge (both raidz and single-disk)
  With a single-disk pool (Bug A avoided), PG starts and reaches
  "checkpoint complete: end-of-recovery" but the postmaster never logs
  "ready to accept connections". gdb on the wedged guest:
     753 startup proc: exited
     postmaster: epoll_file::wait (ServerLoop), _current_as == AS0 (correct)
     checkpointer + bgwriter: blocked in switch_to, in CHILD COW AS
  Checkpointer kernel-stack wait chain:
     sigprocmask(SIG_SETMASK) -> unwait_for_signal / wait_for_signal
        -> waiters_mutex + std::list node alloc (fork_arena::kernel_heap_scope)
     -> memory::pool::alloc (deep self-recursion) -> pool::add_page
     -> mmu::file_vma ctor / vn_lock  (a file-backed mmap allocation)
  This is the SAME signature-F allocator-recursion-under-a-lock family that
  commits 1ae2602f9 / f28570733 / c8f9c82b3 (F2a/F2b) were fixing; F2b even names
  "assert(sched::preemptable()) at mmu.cc ... ~1-in-6 at -smp>1 under fork load".
  A residual instance remains on the startup path (the list-node / file_vma
  allocation inside sigprocmask's waiters_mutex critical section, NOT the
  coherent_wait_record that F2b covered). It manifests two ways I saw:
     - assert(sched::preemptable()) abort in page_fault (a COW write-fault in a
       non-preemptable window), fault addr in a child COW AS (0x6001....), OR
     - a plain hang (postmaster waits forever for the wedged checkpointer).
  Boot-reliability measured with the FIX build: single-disk 0/11 reached ready
  (all PG-start-then-hang); raidz 0/8 (all Bug A). Pure HEAD earlier: 1/5 reached
  ready once (the race is intermittent; it has since degraded to ~0/N here).

Neither Bug A nor Bug B is in kill()/signal.cc; the DROP DATABASE fix is inert
until PG is up. ckpt-diag.txt captured a LUCKY boot (PG had reached ready, then
DROP DATABASE hung) -- that same lucky window is what is currently not
reproducing, because Bug A/Bug B now fire first almost every boot.
