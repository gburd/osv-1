WALL 1 (PRIMARY) -- PG PARALLEL QUERY HANGS   [fork-stack / CONF_fork]  ea7caf7b
================================================================================

SYMPTOM
  With max_parallel_workers_per_gather>0, a parallel Gather (e.g. a forced
  Parallel Seq Scan aggregate over pgbench_accounts) hangs forever; block I/O
  fully drained; worked around before with max_parallel_workers_per_gather=0.

gdb ISOLATION (OSv's own gdb helpers: `osv info threads`, `osv thread apply all
bt`, symbols via `osv syms`)
  * The postmaster thread parks in the normal idle wait:
      ServerLoop -> WaitEventSetWait -> epoll_wait (waiteventset.c:1191)
  * The parallel LEADER + would-be workers are parked; block I/O is drained
    (the virtio::blk::req_done() waiters are idle -- nothing in flight).
  * DECISIVE: with log_min_messages=debug1, running the parallel query emits
    ZERO "starting background worker" lines -- the parallel workers are NEVER
    forked.  The leader waits in WaitForParallelWorkersToAttach for workers
    that do not exist.

ROOT CAUSE (which primitive diverged cross-AS, and why)
  PostgreSQL launches parallel workers by calling RegisterDynamicBackgroundWorker
  in the leader, which fills a shared request slot and then signals the
  postmaster to fork them:  kill(PostmasterPid, SIGUSR1).
  The postmaster is the top-level app / AS0, whose getpid() is OSV_PID (== 2).
  The CONF_fork kill() path (libc/signal.cc) resolved a cross-"process" target
  with osv::fork::as_for_pid(pid) and returned ESRCH when that was null:
      if (pid != getpid() && pid != 0 && pid != -1) {
          target_as = as_for_pid(pid);
          if (!target_as) { errno = ESRCH; return -1; }   // <-- fires for OSV_PID
      }
  AS0 is NEVER entered into g_pid_as (only fork children are register_pid()'d),
  so as_for_pid(OSV_PID) == nullptr, and kill(OSV_PID, SIGUSR1) issued by a
  forked backend (the leader) returned ESRCH -- the signal was DROPPED.  The
  postmaster, parked in its epoll_wait ServerLoop, never saw the bgworker
  request, never forked a worker, and the leader hung.  Pure coordination
  lost-wakeup with I/O drained -- the SAME per-fork-child-pid signal-routing
  class as the shipped SIGCHLD / SIGURG-latch fixes, on the postmaster-bound
  (OSV_PID/AS0) side rather than the child-to-child side.
  (This also explains the previously-noted SIGHUP-to-postmaster ESRCH from
  pg_reload_conf(): same kill(OSV_PID) drop.)

FIX  (libc/signal.cc, #if CONF_fork)
  Exclude OSV_PID from the cross-process target resolution -- treat it like the
  self/broadcast case so target_as stays nullptr and the handler runs in AS0
  (mmu::kernel_address_space()), exactly where the postmaster's handler must run
  to poke its own latch/self-pipe and wake ServerLoop:
      if (pid != getpid() && pid != 0 && pid != -1 && pid != OSV_PID) { ... }
  Never returns ESRCH for the top-level app.  conf_fork=0 does not compile this
  block (byte-identical).

WALL 2 -- ZIL REPLAY WITH sync=standard   [#1423 / OpenZFS]  patch 0029 (009234b4)
================================================================================

SYMPTOM
  A kill -9 mid-txg with sync=standard (ZIL active on the SLOG vblk5), then a
  re-import, either:
    - SPL PANIC in abd_alloc_linear (VERIFY3U(size <= SPA_MAXBLOCKSIZE), wild
      ~18 EiB size), or
    - "Solaris: WARNING: ZFS replay transaction error 95, dataset pgdata,
      txtype 9" (then txtype 10) -- error 95 == EOPNOTSUPP.
  The pool itself is clean (scrub 0 errors); the failure is in ZIL REPLAY.

ROOT CAUSE
  The OSv OpenZFS platform layer left two vnops as ENOTSUP stubs, both on the
  ZIL replay path that runs on import after a crash:
    zfs_replay_write()    (TX_WRITE,   txtype 9)  -> zfs_write_simple()  = ENOTSUP
    zfs_replay_truncate() (TX_TRUNCATE, txtype 10) -> zfs_space(F_FREESP) = ENOTSUP
  So every logged intent-log record was dropped (error 95) -- the ZIL gave no
  durability -- or an incomplete replay read a garbage record size and paniced.
  sync=standard was therefore unusable through the ZIL on OSv.

FIX (modules/open_zfs/patches/0029-*.patch -- an upstream-source change, so a
patches/ entry git-apply'd to the pinned submodule at build time, NOT a
submodule edit; NOT CONF_fork-gated -- single-process correctness)
  * zfs_write_simple(zp, data, len, pos, resid): build a one-iovec struct uio
    over the kernel buffer (UIO_WRITE, offset=pos, resid=len), wrap in zfs_uio_t,
    call the platform-independent zfs_write(zp,&zuio,O_SYNC,NULL) -- the
    zfs_vop_write() shape / FreeBSD's vn_rdwr(UIO_SYSSPACE, IO_SYNC); refresh
    vp->v_size from zp->z_size on success (read-after-write coherence).
  * zfs_space(zp,cmd,bfp,flag,offset,cr): validate F_FREESP, refuse read-only /
    negative len, check ACE_WRITE_DATA, delegate to the already-present
    zfs_freesp(zp,off,len,flag,TRUE) -- identical to FreeBSD's zfs_space.

VALIDATION (pasted)
  --- re-import after sync=standard kill -9: no error, no panic ---
    (before) Solaris: WARNING: ZFS replay transaction error 95 ... txtype 9/10
    (after)  -- replay-error check --  (no ZIL replay error, no panic)
             LOG: database system is ready to accept connections
  --- sync=standard durable marker survives crash + reboot on the RAID-Z ---
    PHASE 1: insert (1,'RAIDZ-DURABLE-MARKER'); checkpoint;  -> row present
             kill -9 (crash), sync=standard
    PHASE 2: re-import -> PG crash recovery -> ready
             select * from durx;
               1 | RAIDZ-DURABLE-MARKER      <=== DURABLE with sync=standard

SCOPE / HONEST NOTE
  The two replay ops (TX_WRITE, TX_TRUNCATE) are the ones PG's fsync-heavy
  workload logs to the ZIL; both now replay and a sync=standard pool re-imports
  cleanly and serves correct data after a crash.  Remaining ZIL replay ops that
  build directory/namespace state (TX_CREATE/MKDIR/REMOVE/LINK/RENAME/SETATTR,
  and the ACL/attr variants) are still stubbed: a crash in the MIDDLE of a DDL
  statement whose namespace op is only in the ZIL (not yet in a txg) can leave a
  catalog inconsistency (observed once as "pg_attribute catalog is missing ...").
  This does NOT affect the durability of committed DATA (heap/index writes =
  TX_WRITE, now replayed) or a crash after a checkpoint; HammerDB TPROC-C is a
  fixed-schema OLTP workload (no concurrent DDL under load), so sync=standard is
  sound for the benchmark.  Implementing the full namespace replay vector is the
  bounded follow-on if concurrent-DDL crash consistency is ever required.
