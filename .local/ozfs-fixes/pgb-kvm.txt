--------------------------------------------------------------------------------
FINDING #1 (decisive) -- pgbench -i -s 1000 FAILS on OSv-KVM OpenZFS raidz
--------------------------------------------------------------------------------
-s 1000 = 100M-row (~15GB) bulk COPY. TWO reproducible failure modes, both in
the ZFS bulk-write path once a PG relation grows past the 1GB segment boundary
(pgbench_accounts at s=1000 is ~13GB -> segments base/5/16399, .1, .2 ...):

  ATTEMPT 1: COPY completed 100M rows in 91s (~1.1M tuples/s, guest stable),
    then the "creating primary keys" checkpoint CRASHED the guest:
      Assertion failed: owner.load(std::memory_order_relaxed) ==
        sched::thread::current()  (core/lfmutex.cc: unlock: 261)
      [backtrace] lockfree_mutex_unlock+470 <- <ZFS cb> <- taskqueue_thread_loop+82
                  <- thread_main_c
    = a ZFS-taskqueue lockfree mutex UNLOCKED from a different thread than
      locked it (cross-thread/cross-AS lfmutex ownership violation). Same
      taskqueue class as the prior KVM cell's arc_write_done crash, different
      exact site (lfmutex owner mismatch on the CREATE INDEX + checkpoint path).

  ATTEMPT 2 (fresh re-seeded pool): failed EARLIER, during the COPY itself, at
    the 1GB segment rollover:
      ERROR: could not open file "base/5/16399.1" (target block 131072): EIO
      CONTEXT: COPY pgbench_accounts, line 7992000
    (131072 * 8KB = exactly 1GB = PG's next relation segment .1). The EIO then
    POISONED the pool: subsequent reads also EIO
      FATAL: could not open file "base/5/PG_VERSION": EIO
    i.e. the OpenZFS-on-OSv raidz went into a suspended/errored state after the
    large-file write fault; the mount is unusable until re-seed.

VERDICT: -s 1000 (and by extension any dataset whose relations cross the 1GB PG
  segment boundary under sustained bulk write) is NOT viable on OSv-KVM OpenZFS
  raidz today. This is the SAME wall class the prior KVM cell documented for the
  HammerDB TPROC-C schema build (bulk COPY in the ZFS taskqueue/ARC write path).
  Root cause lives in the ZFS large-file / taskqueue-mutex write-completion path
  under fork; a real OSv+OpenZFS finding, NOT a pgbench/config issue.

(3) THE WALL THIS KVM BOX ACTUALLY HITS (reproduced, decisive): RW WRITE PATH
--------------------------------------------------------------------------------
Not the catalog READ wall -- the ZFS WRITE-completion taskqueue. Two repros:

 * pgbench -i -s 1000 (100M-row / ~15GB bulk COPY): FINDING #1 above -- either a
   lfmutex owner-mismatch crash on the CREATE INDEX + checkpoint, or an EIO at
   the 1GB PG-segment rollover that then poisons the pool (reads EIO).

 * pgbench RW sweep at s=100 (the proven-stable scale): the sweep produced REAL
   numbers for the first two runs --
     off-s100 rw c=1 it=1 : tps=283.75  lat=3.524 ms  0 failed
     off-s100 rw c=1 it=2 : tps=285.38  lat=3.504 ms  0 failed
   -- then on the 3rd RW run the guest CRASHED with the same signature as -s1000
   attempt 1:
     Assertion failed: owner.load(std::memory_order_relaxed) ==
       sched::thread::current()  (core/lfmutex.cc: unlock: 261)
     [backtrace] lockfree_mutex_unlock+470 <- <ZFS cb>
                 <- taskqueue_thread_loop+82 <- thread_main_c

   pgbench" numbers were a warm/short-lived fluke: sustained RW load crashes the
   guest in the ZFS write-completion taskqueue. This is the real OSv+OpenZFS+fork
   wall to fix (same class the prior KVM cell tagged: arc_write_done / taskqueue
