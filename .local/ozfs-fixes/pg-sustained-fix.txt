VERDICT (one line)
================================================================================
The sustained-serving wall is candidate (c) as predicted: the application_
runtime shared_ptr (object + control block) lived in COW/arena memory (VA
0x3000..) exactly like the DSM registry nodes did.  gdb proved it directly.
The fix is the SAME proven pattern -- force the fork-shared kernel structure
onto the identity kernel heap (fork_arena::kernel_heap_scope) so it is byte-
identical in every address space, never a COW-private arena copy.  A second
structure (virtio-net's TX net_req, alloc'd in a backend AS but free'd cross-AS
by txq::gc) needed the same treatment; with both, PG serves sustained
connections.  A THIRD, DISTINCT wall (shared-buffer/ramfs write coherence under
a heavy pgbench -i bulk load) is precisely symbolized but NOT fixed here -- it
is a storage-coherence wall, separate from the fork/reap lifecycle this report
closes, and it does NOT block sustained connection serving.

Inspecting the fork()'ing thread's _app_runtime at the fault:

  (gdb) p sched::thread::current()->_app_runtime._M_ptr
    $ = 0x3000000004a0                       <- IN THE FORK ARENA (arena_base 0x300000000000)
  (gdb) p *sched::thread::current()->_app_runtime._M_ptr
    $ = {app = @0x202000ae4bc0210}           <- `app` reference is WILD GARBAGE
  (gdb) p &(runtime._M_ptr->app)
    $ = (osv::application *) 0x202000ae4bc0210
  (gdb) p/x _app_runtime._M_refcount._M_pi
    $ = 0x3000000004e0                        <- control block ALSO in the arena

Two runs showed the `app` reference as 0x202000ad0c00210 and 0x202000ae4bc0210 --
it VARIED run-to-run: the signature of a COW-divergent read of the SAME arena VA,
not a fixed dangling pointer.

MECHANISM (candidate c, confirmed): PostgreSQL runs as ONE osv::application (the
postmaster, launched from the kernel loader path).  Its application_runtime is
created once in the application ctor: `_runtime(new application_runtime(*this))`.
That `new` (and the shared_ptr control block) was executed on an APP thread, so
std_malloc routed it into the COW fork arena (VA 0x3000..).  Every forked
backend thread's _app_runtime points at that arena object (thread ctor:
`_app_runtime = app->runtime()`).  clone_address_space() COW-clones the whole
arena per fork.  Across many fork/reap cycles (with overlapping live backends)
the arena page backing the runtime diverges, so the fork()'ing thread eventually
reads a runtime copy whose `app` reference field holds garbage.  get_current()
then does runtime->app.get_shared() -> enable_shared_from_this::shared_from_this
reads _M_weak_this at (garbage application*)+8 -> inaccessible -> GP fault, which
KVM escalates to "exception nested too deeply".

This is exactly the rule from the DSM milestone (pg-dsm-fix.txt): any kernel
structure a forked child / RX-IRQ thread / reaper reads must live on the
identity kernel heap, never the COW fork arena.

================================================================================
THE FIXES (minimal, correct, #if CONF_fork; non-fork byte-identical)
================================================================================
1. core/app.cc -- THE SUSTAINED-SERVING FIX.
   Allocate the application_runtime AND its shared_ptr control block on the
   identity kernel heap via make_shared under fork_arena::kernel_heap_scope
   (make_shared co-allocates object + control block in ONE block, so one scope
   covers both).  The ctor's member-init list calls a small helper
   make_identity_heap_runtime(*this) under CONF_fork; the non-fork build keeps
   the exact original `_runtime(new application_runtime(*this))`.

2. drivers/virtio-net.cc -- THE NET-TX net_req FIX (uncovered after fix 1).
   Once PG served past ~50 connections, a NEW wall appeared:
     Assertion failed: h->magic == chunk_magic (core/fork_arena.cc recover:257)
       fork_arena::free(void*)+72
       virtio::net::txq::gc()+88            ; delete req
       virtio::net::txq::try_xmit_one_locked
       osv::xmitter<..>::xmit(mbuf*)
       ether_output / ip_output
   net::txq::xmit_prep() does `net_req* req = new net_req(m_head)` on the TX
   submit path -- run by an app-thread backend sending its query response, so
   the net_req landed in the arena.  txq::gc() later delete's it from a
   DIFFERENT thread/AS as the host completes the send; free()-by-address then
   read a divergent/garbage arena chunk header (magic mismatch) in the reaping
   AS -> assert.  Fix: wrap the `new net_req` in kernel_heap_scope so it lands
   on the identity heap; delete (which dispatches by address) then frees it
   correctly from any AS.  Same rule as mbufs / thread stacks / the app runtime.

Both changes vanish in the conf_fork=0 build (the guards compile away; the
app.cc #else restores the byte-identical original).

================================================================================
THE REGRESSION TEST -- tests/tst-fork-serial.cc (author Greg Burd)
================================================================================
Registered in modules/tests/Makefile.  Mirrors PG's postmaster: keep a rolling
window of overlapping live children while continuously fork()ing new backends
and reaping the oldest, 30 iterations.  Each child does a little real work
(heap alloc+write, a .data COW write, a getpid syscall, heap churn) and exit()s
with a distinct code the parent waitpid-verifies; the postmaster churns its own
arena heap between forks.  Every new-thread ctor runs application::get_current()
-- the faulting path.

HONEST NOTE (in the test's header too): the DEFINITIVE reproducer of the GP
fault is PostgreSQL itself (~6-7 sequential connections; the gdb backtrace
above).  This synthetic loop does NOT by itself corrupt the arena runtime,
because the arena bump allocator hands application_runtime a stable low VA that
is never recycled, and COW divergence only touches pages a process actually
WRITES -- and nothing in the synthetic loop writes the runtime's page.  The PG
corruption additionally involves the network/DSM/signal write patterns a real
postmaster exercises across its address space.  tst-fork-serial is therefore
the fast, PG-free OS-level GUARD for the fixed code path (sustained overlapping
fork/work/exit/reap with get_current() on every new-thread ctor); it must stay
green.  It PASSES with the fix; it guards against any change that reintroduces a
get_current() fault on the common fork path.

NEXT WALL (distinct, precisely symbolized, NOT fixed here -- honest)
================================================================================
HEAVY BULK-LOAD / STORAGE-COHERENCE, under `pgbench -i` (scale 5), NOT a
fork/reap fault:

  (a) parallel index build reported "invalid page in block N of relation ...";
      a parallel worker (PID 404) exited code 1.  (Parallel workers share
      buffers via DSM; a buffer/page-coherence issue under the parallel build.)
  (b) then a checkpoint / large ramfs write faulted:
      page fault outside application, addr: 0x0000200014359000
      RIP: memcpy_repmov_ssse3+74
        RDI(dest)=0x200014359040 (an app-slot MAP_SHARED/mmap region, UNMAPPED
        in the writing backend's AS), RSI(src)=0x30001ade4000 (arena)
        pwrite64 -> sys_write -> vfs_file::write -> (ramfs write) -> memcpy
      i.e. a ramfs write memcpy'd into a shared-buffer mmap region that is not
      present in the current backend's page tables.

This is a STORAGE / shared-buffer mmap coherence wall (a MAP_SHARED region not
mapped in a forked backend's AS during a large write / checkpoint), separate
from the fork/reap lifecycle this report closes.  It does NOT block sustained
CONNECTION serving (100 sequential + 40 concurrent + 12 DML rounds all pass);
it surfaces only under the heavy pgbench -i bulk load + parallel workers +
checkpoint.  It is the next investigation for a full HammerDB run.

Do NOT read this as "PG is production-ready on OSv": pgbench -i heavy bulk load
trips the storage-coherence wall.  But the milestone asked for here -- SUSTAINED
serving of many sequential + concurrent connections -- IS achieved, with the
verbatim output above.

the SAME rule as the shipped struct-file / signal-table / thread-object / arena-
