*** CORRECTED DIAGNOSIS (the earlier "CHECKPOINT hangs" guess was WRONG) ***
********************************************************************************
The stuck operation is NOT a checkpoint. Explicit CHECKPOINT COMPLETES on OSv+PG
(twice, verbatim below, in ~0.03s). What hangs forever is:

    DROP DATABASE  ->  EmitProcSignalBarrier(PROCSIGNAL_BARRIER_SMGRRELEASE)
                   ->  WaitForProcSignalBarrier(...)  <-- never returns

The issuing backend (PID 803) logs, every 5s, indefinitely:
    LOG:  still waiting for backend with PID 803 to accept ProcSignalBarrier
i.e. it is waiting for ITS OWN backend to acknowledge a global ProcSignalBarrier.
The self-directed barrier interrupt/ack is never processed on OSv, so the
per-backend pss_barrierGeneration never catches up to the emitted generation and
WaitForProcSignalBarrier() spins forever. A concurrent lightweight query
(`select 1`) returns INSTANTLY -- it never touches the barrier machinery -- which
is why the guest looks "alive" while the DROP DATABASE session is wedged.

This is the SAME lost-signal / cross-fork-AS wakeup-coherence class as the
documented startup-handoff wall and the logical-replication-launcher hang, but
on the ProcSignalBarrier delivery path. PostgreSQL uses ProcSignalBarrier for
global invalidations: DROP DATABASE, DROP TABLESPACE, and SMGR-release events
broadcast a barrier and WAIT for every backend (including the emitter) to ack it
via the ProcSignal SIGUSR1 -> ProcessProcSignalBarrier() path. On OSv's
thread-backed forked backends, the emitter's own barrier-ack does not fire.

--------------------------------------------------------------------------------
WHAT TRIGGERED IT IN THE HARNESS
--------------------------------------------------------------------------------
Not the workload. During external-path setup the driver hit a musl-locale snag
(client tried locale "C.UTF-8", which musl PG lacks -> ENOENT), so the bench DB
was being drop+recreated with an explicit C locale. That routine `DROP DATABASE
IF EXISTS bench;` is what wedged. So the wedge is reachable by ANY DROP DATABASE,
not a heavy-write corner. (The GO gate's pgbench -c16 -T120 never ran DROP
DATABASE, which is why it completed cleanly with background checkpoints -- it
simply never exercised the ProcSignalBarrier broadcast path.)

Note the locale snag separately (harness, not a bug): musl PG on OSv has no
"C.UTF-8" locale data; create benchmark DBs with template0 + LC_COLLATE=C
LC_CTYPE=C (encoding SQL_ASCII or LATIN1), and avoid clients that force C.UTF-8.

--------------------------------------------------------------------------------
WHERE TO LOOK (fix pointers)
--------------------------------------------------------------------------------
PostgreSQL side:
  src/backend/storage/ipc/procsignal.c
    EmitProcSignalBarrier() / WaitForProcSignalBarrier() / ProcessProcSignalBarrier()
    CheckProcSignalBarrier() -- called from CHECK_FOR_INTERRUPTS().
  The emitter sets ProcSignalBarrierPending for all backends (itself included)
  and waits on pss_barrierGeneration. The ack is driven by SIGUSR1 (procsignal_
  sigusr1_handler -> sets the flag) and then ProcessProcSignalBarrier() runs at
  the next CHECK_FOR_INTERRUPTS(). If OSv does not deliver the self-SIGUSR1 (or
  the forked-backend's signal state / latch does not observe it), the emitter
  never runs ProcessProcSignalBarrier() on itself -> its own generation never
  advances -> WaitForProcSignalBarrier spins.

OSv side (most likely root, same class as the known walls):
  - Self-directed signal delivery to a forked (thread-backed) backend: does
    kill(getpid(), SIGUSR1) / the ProcSignal SetLatch reach the emitter's own
    signal-handling in the OSv fork_arena model?
  - Latch/SetLatch wakeup coherence across the fork COW AS boundary (same
    lost-wakeup family as pg-zfs-validate.txt "THE NEXT WALL" and the
    logical-replication-launcher startup hang).
  Reproduce with a tiny case: boot the guest, `psql -c 'CHECKPOINT'` (works),
  then `psql -c 'DROP DATABASE IF EXISTS x'` on a nonexistent DB still emits the
  barrier? -- if not, `CREATE DATABASE x TEMPLATE template0; DROP DATABASE x;`
  wedges deterministically. Attach gdb via qemu `-s` and break in
  WaitForProcSignalBarrier to inspect pss_barrierGeneration vs the backend's
  pss_barrierGeneration and whether ProcSignalBarrierPending is still set.

IMPACT ON THE BENCHMARK
--------------------------------------------------------------------------------
Blocking: the harness reseeds/cleans between cells and would issue DROP DATABASE
(and CREATE DATABASE cleanup). More importantly it is a correctness/reliability
bug for real PG-on-OSv use (any DROP DATABASE / DROP TABLESPACE wedges). Since a
fix touches the signal/latch path -- the exact machinery the parity benchmark is
meant to measure -- the benchmark is halted and will be re-run clean after the
fix. No numbers were fabricated; 0 cells banked.

Workaround for the eventual benchmark (once past this / if needed): reseed
between cells by IMPORTING A FRESH POOL COPY (re-run the cpiod seed onto a
freshly created pool) instead of DROP DATABASE + reload, and skip explicit
pre-reboot CHECKPOINT (checkpoint works, but dirty reboot recovers cleanly
anyway: the GO run proved WAL redo + scrub-0-errors on a hard stop, ~75s budget).
