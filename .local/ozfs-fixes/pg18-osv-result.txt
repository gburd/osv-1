Configure: --without-icu --without-zlib --without-readline --without-libxml
           --without-libxslt
CFLAGS   = -O2 -g -fPIC -fPIE -U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0
           -DWAIT_USE_SELF_PIPE
LDFLAGS_EX = -pie          <-- CRITICAL. Put -pie in LDFLAGS_EX, NOT global
             LDFLAGS: LDFLAGS pollutes the loadable-.so conversion modules
             (euc_kr_and_mic.so etc.) and breaks the link ("undefined ref main").
Result: postgres = ELF DYN, FLAGS_1: PIE  (OSv type-2 dynamically-linked PIE).
OSv-relevant fact: OSv's kernel SUPPLIES libc.so.6 / libm.so.6 / libresolv /
ld-linux as built-in modules, so the PG PIE resolves its only deps against OSv's
built-in libc. No glibc is baked into the image. PG runs on OSv's libc(=musl-ish
+ glibc-compat) via the ld-linux shim.

Two SOURCE deviations from stock (each an OSv-environment adaptation, each 1 line,
each clearly an OSv-vs-Linux gap, NOT a fork workaround):
  - -DWAIT_USE_SELF_PIPE  : PG18's default latch uses signalfd()+epoll for SIGURG
    (waiteventset.c). OSv stubs signalfd()->ENOSYS ("FATAL: signalfd() failed").
    WAIT_USE_SELF_PIPE is PG's OWN supported portable fallback (self-pipe+poll);
    a build-time knob, not a patch.
  - check_root() neutered (main.c): PG refuses to run as root; OSv makes every
    process uid 0 (geteuid() hardcoded to 0, no user model). 1-line body no-op.
  - checkDataDir() perm check neutered (miscinit.c): OSv filesystems report fixed
    modes (rofs 0555, ramfs 0777), not the 0700/0750 PG demands. 1-line no-op,
    mirrors PG's own "XXX suppress on Windows, no Unix-y perms" comment.

--------------------------------------------------------------------------------
(e) WHERE it breaks — full chain, each finding empirical
--------------------------------------------------------------------------------
i.   root check          -> geteuid()==0 on OSv. (env gap; neutered)
ii.  signalfd()          -> ENOSYS on OSv. (PG18 latch; -DWAIT_USE_SELF_PIPE)
iii. empty cluster dirs  -> "**" glob skips them. (manifest fix)
iv.  AF_UNIX socket      -> "Address family not supported by protocol". OSv has
                            partial af_local but PG's socket setup fails. Set
                            unix_socket_directories='' (TCP-only; client uses the
                            forwarded TCP port anyway).
v.   writable /data      -> PG must write WAL/etc.; rofs is read-only (getattr
                            0555). Used fs=zfs (writable). ZFS mounts with a
                            benign "replay transaction error 95" warning.
                            (fs=ramfs was blocked by a bootfs libsolaris/mount-fs
                            tool dependency in the module-only build.)
vi.  PG18 io_method       -> default IOMETHOD_WORKER forks io_worker at startup;
                            that fork crashed. Set io_method=sync to defer forking
                            to the startup process — which ALSO crashed the same
                            way. So it is the fork itself, not a specific child.

vii. THE ROOT-CAUSE CRASH (found + FIXED here):
     The postmaster's first fork()'d child aborted with OSv:
        "trying to execute null pointer"  (page_fault, ef->rip == 0)
     Instrumenting PG's fork_process() child path showed the child ran
     fork()->getpid() fine, then died on its NEXT libc call (a glibc write()).
     Instrumenting OSv arch/x64/fork.cc revealed WHY:
        parent_app_tcb   = 0x0
        parent_real_fsbase = 0x500001fd2880   (the postmaster's glibc TLS base)
        child_app_tcb    = 0x0
     OSv's fork_thread set the child's TLS from get_app_tcb(), but the app's
     MAIN thread (postmaster) has app_tcb==0 while running on a real non-zero
     fsbase. So the child ran with OSv's kernel-thread fsbase, and glibc code in
     the child read TLS from the wrong base -> jumped through garbage -> RIP=0.
     FIX (applied to arch/x64/fork.cc): read the parent's live fsbase directly
     (processor::rdmsr(IA32_FS_BASE)) and, when app_tcb==0, set the child's
     fsbase to that. After the fix the child gets PAST the crash (markers
     CHILD:after-getpid and CHILD:pre-getenv now print).

viii.THE REMAINING WALL (NOT fixed — fundamental to OSv single-address-space):
     With the fsbase fix the child now HANGS in the very next libc call,
     getenv("PG_OOM_ADJUST_FILE"), and never returns (VM killed at timeout).
     Cause: OSv fork() gives the child a private STACK but SHARES the parent's
     TLS block (same fsbase) AND heap/dynamic-linker locks. Real fork() gives the
     child a PRIVATE copy of TLS. With parent and child live on one shared TLS,
     glibc per-thread state / libc & ld.so locks are corrupted or deadlock, so
     the first nontrivial glibc call in the child (getenv) hangs. This is exactly
     the shared-heap/single-address-space limitation the experiment set out to
     probe.

--------------------------------------------------------------------------------
WHAT WOULD BE NEEDED NEXT (for a future run)
--------------------------------------------------------------------------------
Give the forked child a PRIVATE TLS copy: allocate a new TLS/TCB block, copy the
parent's glibc TCB + static-TLS into it, and point the child's fsbase at the
copy (like clone()/pthread_create does via CLONE_SETTLS). This is non-trivial
because the glibc TCB size/layout is opaque to OSv (glibc, loaded via ld-linux,
manages its own TLS, which is why app_tcb is 0 for the main thread). Not
attempted here. Until then, fork-per-backend PostgreSQL will not run on OSv.

Also worth doing: teach OSv's geteuid/perm model, af_local, and signalfd enough
that stock PG needs zero source edits; and wire a proper apps/postgres18 that
builds ramfs (writable, no ZFS replay warning).
