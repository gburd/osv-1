HEADLINE (honest)
================================================================================
* Firecracker BOOT / RAID-Z STORAGE / CROSS-INSTANCE NETWORK == KVM: PROVEN.
  OSv boots under FC v1.7.0 in ~135 ms, the raidz1(4xEBS)+SLOG+L2ARC pool
  imports/mounts/scrubs 0-errors, and an EXTERNAL c5.4xlarge driver reaches
  PG18.4-musl on the DB host private IP :5432 over the ENI DNAT -> tap ->
  virtio-net path.  Real cross-instance TCP.  Byte-identical behavior to the
  OSv-KVM cell for boot+storage+net.

* pgbench TPC-B DOES NOT RUN on tip 3f20fef46: `pgbench -i -s 1000` fails at
  `CREATE TABLE pgbench_history(... mtime timestamp ...)` with
      ERROR: type "pg_catalog.timestamp" does not exist
  because the pg_type index B-tree page holding the `timestamp` entry reads back
  as a ZERO PAGE through the OSv fork/COW shared-buffer path.  The on-disk pool
  is provably intact (scrub 0B/0 errors; a seqscan of pg_type FINDS timestamp
  oid 1114 + timestamptz 1184; 621 pg_type rows present).  It is an INDEX-page
  read-zero, i.e. the documented OSv fork/COW shared-buffer/catalog coherence
  wall -- NOT storage, NOT a bad seed, NOT Firecracker.

* The "fixed elsewhere" premise does NOT hold on this image tip.  The
  multi-backend / catalog-index-page COW coherence wall is STILL OPEN on
  3f20fef46.  It caps concurrency hard (16 concurrent logins: OK=1, FAIL=15)
  and blocks even single-connection pgbench init.  I did NOT fabricate a tps
  number.

* FC == KVM verdict: BEHAVIORALLY IDENTICAL.  Same boot, same raidz, same
  cross-instance serving, same single-persistent-backend success, and the SAME
  fork/COW catalog-index zero-page wall.  No hypervisor-specific divergence.
  (The prior FC cell + the KVM cell's own FC cross-check reached the same
  hypervisor-independent conclusion; this cell reproduces it on a fresh box +
  fresh build of tip 3f20fef46.)

    is hypervisor-INDEPENDENT.  FC reproduces KVM exactly; the storage +
    network + boot paths are stable and identical.

================================================================================
ANSWERS TO THE HEADLINE QUESTIONS
================================================================================
Q: Does OSv-Firecracker == OSv-KVM on a steady-OLTP (pgbench TPC-B) workload?
A: For BOOT + RAID-Z STORAGE + CROSS-INSTANCE NETWORK + single-backend SQL: YES,
   behaviorally identical (FC virtio-MMIO reproduces KVM virtio-PCI).  For the
   pgbench TPC-B WORKLOAD ITSELF: neither hypervisor produces a number on tip
   3f20fef46 -- both are blocked by the SAME hypervisor-independent OSv fork/COW
   catalog-index zero-page wall.  So FC == KVM including the wall.  No
   FC-specific divergence found (one FC-only cosmetic net quirk: needs a static
   host neigh for the guest; non-fatal).

Q: Did OSv+PG survive pgbench TPC-B, as the premise assumed?
A: NO on this image tip (3f20fef46).  The fork/COW shared-buffer/catalog-index
   coherence wall the premise says is "fixed elsewhere" is STILL OPEN here.  A
   single persistent connection is stable and does correct SQL + durable writes
   on the raidz; pgbench (which needs the timestamp type at init and concurrent
   client backends at run) hits the catalog-index zero-page and cannot init or
   sweep.  Storage/network/boot are solid.  Honest verdict: not yet a pgbench
   tps number.

Q: What did huge pages buy?
A: Irrelevant to this result -- the wall is huge-page-independent and config-
   independent (fails identically with huge_pages off, default vs 8GB
   shared_buffers).  No tps to compare, so no huge-page delta measured.

MATRIX (rows intended vs what the fork wall permits) -- see pgb-fc.tsv:
  config  | hugepages | mode | clients      | tps/latency | note
  osv-fc  | off/on    | rw   | 1,4,8,16,32,64 | N/A (BLOCKED) | pgbench -i fails at CREATE TABLE timestamp
  osv-fc  | off/on    | ro   | 1,8,16,32,64   | N/A (BLOCKED) | needs the same -i data
  (KVM control on this class of image: identical wall -- OSv-common, not FC.)

DIFFERENCES FROM KVM (the "FC==KVM?" answer, valuable per the ask):
  * BOOT: identical (FC ~135ms; both mount ZFS root, bring up eth0).
  * STORAGE: identical (same raidz geometry/props, scrub 0-errors, single-backend
    durable writes round-trip).
  * NETWORK: identical DNAT model; ONE FC-only operational quirk -- OSv
    virtio-net-MMIO under FC needs a static host ARP entry for the guest MAC to
    make the ENI DNAT path reliable (KVM virtio-PCI did not).  Cosmetic, non-fatal.
  * WORKLOAD WALL: identical -- same fork/COW catalog-index zero-page,
    hypervisor-independent.
