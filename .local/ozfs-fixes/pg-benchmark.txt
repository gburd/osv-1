## HONEST READ OF THE LINUX NUMBERS
################################################################################
* Scaling is clean and monotonic 8->64 VU both hp states; iteration variance is
  small (e.g. hp=off 16VU: 61,003..61,132, <0.3% spread) -> the medians are
  trustworthy.
* hp=on is the winner at high concurrency (64 VU: 115,463 vs 103,826 NOPM, hp=on
  +11%). At low/mid VU hp=OFF reads higher (8 VU: 39,235 vs 27,796) -- but the
  hp=on 8-VU point has the widest spread (25,249..31,279), i.e. the hp=on 8VU
  iter1 (25,249) was a cold-cache/L2ARC-warmup artifact; hp=on 8VU iter3 already
  reached 31,279. Read the 8-VU cell as noisy warmup, not a real hp regression.
  The defensible statement: at the saturating point (64 VU) hugepages buy ~+11%
  NOPM on this NUMA-local, 8GB-shared_buffers, raidz-I/O-bound config.
* At 8/16 VU the DB host CPU was ~96% idle (I/O-latency bound on raidz, not CPU);
  CPU utilization climbs toward 64 VU as concurrency fills the node-0 cores.
  This is expected TPROC-C-on-durable-storage behavior.

## OSv FINDINGS (the walls before the OSv sweep can run) -- IMPORTANT, HONEST
################################################################################
FINDING #1 (blocker, not a crash) -- musl has no C.UTF-8 locale
  The OSv cluster initdb'd with collation C / ctype C / encoding UTF8. HammerDB's
  CREATE DATABASE resolves the new DB's collation to "C.UTF-8" (PG18 default for
  a UTF8 DB), which is INCOMPATIBLE with the template's pure "C":
     ERROR: new collation (C.UTF-8) is incompatible with the collation of the
            template database (C)
  Creating tpcc explicitly AS C.UTF-8 succeeds, but then OPENING it fails:
     DETAIL: the operating system could not find any locale data for the locale
             name "C.UTF-8"
  because musl (OSv libc) ships no C.UTF-8 locale data. Linux (glibc) has
  C.UTF-8, which is why config 1 built with no locale friction. This is a musl
  vs glibc locale-data gap, NOT a PG-on-OSv logic bug. FIX PATH (bounded):
  initdb/seed the OSv cluster's template with a musl-available locale and have
  HammerDB target C encoding (SQL_ASCII/C works -- TPROC-C data is ASCII), OR
  add C.UTF-8 locale data to the OSv musl image. Either unblocks the OSv sweep.

FINDING #2 (crash, reproducible) -- OSv guest page-fault on a CREATE DATABASE path
  While working around #1, `CREATE DATABASE ... TEMPLATE template0 LC_COLLATE 'C'`
  (a locale-MISMATCHED template0 copy) aborted the OSv guest with a NULL deref:
     page fault outside application, addr: 0x0000000000000000
     RIP: 0x00000000402b51e5 ... Aborted
     [backtrace] 0x4020277e 0x40205974 0x4030cabb 0x4030b7f2 0x403d88e4
                 0x40388557 0x403885eb 0x40387d27 0x4030c9c1
  IMPORTANT nuance: the SAME statement with a MATCHED collation
  (`TEMPLATE template0 LC_COLLATE 'C.UTF-8'`) returned "CREATE DATABASE"
  successfully and the guest survived -- so the crash is on the ERROR/cleanup
  path of a rejected createdb (a null pointer dereferenced while unwinding the
  collation-mismatch error inside the forked backend / copydir teardown), not on
  the happy path. This is a NEW OSv wall (kernel-side null deref on a PG error
  unwind), in the same family as the shipped fork_arena cross-AS fixes. It needs
  a gdb walk (osv syms + break on the fault) to pin the deref -- the RIP/backtrace
  above is the seed. It did NOT corrupt the pool (raidz stayed ONLINE, re-seeded
  clean each time).

  => The OSv sweep is one locale fix (#1) + one null-deref fix (#2) away from
     running. Both are characterized with a repro; neither was reachable to fix
     before the host was terminated out from under the run.
