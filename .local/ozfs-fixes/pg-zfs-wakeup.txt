HEADLINE (honest)
================================================================================
* ROOT-CAUSED the "NEXT WALL" from pg-zfs-validate.txt with gdb, and it is the
  predicted class: a LOST WAKEUP in the ZFS synchronous-I/O completion path
  across the fork copy-on-write (COW) address-space boundary -- but bigger than
  a single condvar.  The whole of OpenZFS runs as libsolaris.so loaded into the
  COW-cloned APPLICATION VA slot (slot 32), so EVERY piece of ZFS state a forked
  PostgreSQL backend touches -- statics, heap objects, large hash arrays, and
  the block-I/O bio -- gets a private per-child COW copy, while ZFS's own kernel
  threads run in AS0 and see a DIFFERENT copy.
* FIXED five concrete instances of that class (commit d4c74c94, bundled).  The
  effect is dramatic and monotonic: stock PostgreSQL went from "hangs the instant
  it logs 'database system was shut down'" to COMPLETING FULL CRASH RECOVERY and
  reaching:
      LOG:  database system is ready to accept connections
  on ZFS-on-NVMe (proven with sync=disabled; see below).  psql connects and
  serves `select 1`, `select version()`, `create table`, etc.
* TWO FURTHER WALLS of the same/adjacent class remain (the report predicted
  "1-2 more sites") and BLOCK the acceptance gate (sustained correct queries):
   (A) ZIL lwb synchronous-write completion: with the default sync=standard,
       PG's end-of-recovery fsync -> zil_commit -> zil_commit_waiter blocks in
       cv_wait(&zcw->zcw_cv); the log-write-block (lwb) is stuck in state ISSUED
       and its write ZIO never drives the completion, though the virtio-blk
       completion threads are idle (I/O drained).  Setting the pool
       sync=disabled bypasses the ZIL lwb path and PG reaches "ready" in ~2s.
   (B) forked-backend ZFS WRITES produce NO block I/O: even with sync=disabled
       and PG "ready", a committed heap INSERT is not seen by a subsequent
       SELECT (even in the same backend/session): `INSERT 0 5` then
       `select count(*)` returns 0, with NO server error.  DECISIVE evidence:
       kernel counters in virtio-blk make_request/drain_queue show block
       submitted==completed at ALL times (so I/O COMPLETION is NOT lost -- the
       wakeup fix works), but across `insert; checkpoint` the WRITE counter
       (VIRTIO_BLK_T_OUT) does not move at all (245 -> 245) while reads climb.
       So a forked backend's writes never reach the block device: the dirty
       data goes into ZFS's dbuf/ARC in the backend's address-space view but the
       AS0 txg_sync_thread issues zero write ZIOs for it -- most likely a
       dirty-list linkage the forked backend appends to that AS0 does not
       traverse (dnode/objset/dataset/pool dirty lists).  This is the true
       blocker to "serves concurrent queries with 0 failed" and is a ZFS
       write-path/fork issue distinct from the wakeup class.
* Because of (A)+(B) I have NO honest "PG serves sustained/concurrent queries
  with 0 failed" result to paste.  I will NOT fabricate one.  What IS proven and
  pasted below: PG reaches "ready to accept connections" on ZFS-on-NVMe, accepts
  connections, and answers non-storage queries; and the exact gdb evidence for
  every wall.

THE FIX (commit d4c74c94) -- gdb-proven, #if CONF_fork, non-fork byte-identical
================================================================================
gdb walk of the hang (all vCPUs idle => lost wakeup) resolved the forked startup
process, via a corrected per-child page-table stack unwind, to:
    #3 condvar::wait
    #4 condvar_wait
    #5 zil_commit_impl (== inlined zil_commit_waiter -> cv_wait(&zcw->zcw_cv))
    #6 zil_commit_flags
    #7 zfs_fsync
    #8 sys_fsync / fsync
En route to reaching that point, gdb found (and each fix cleared) these
cross-AS-COW walls, in order:

1. block-I/O bio (fs/vfs/kern_physio.cc, alloc_bio):
   A forked backend submits a synchronous ZFS read/write; the SINGLE virtio-blk
   completion thread (req_done/drain_queue, AS0) reads the bio back
   (bio->bio_caller1 = the zio, bio_done, bio_flags) to complete it.  In the COW
   arena the AS0 thread read a divergent copy -> drove completion against a stale
   zio.  FIX: alloc_bio() allocates on the identity kernel heap.  (Symptom before
   the fix: SIGSEGV in virtio::blk::drain_queue.)

2. zio_t and the entire SPL/ZFS heap (opensolaris_kmem.c):
   zio_t.io_cv (zio_wait vs the AS0 block-completion cv_broadcast in zio_done),
   zil_commit_waiter_t.zcw_cv, dmu_tx/dbuf/dnode/arc_buf_hdr and their embedded
   locks/condvars all come from SPL kmem.  FIX: route zfs_kmem_alloc +
   kmem_cache_alloc onto the identity kernel heap (ZFS objects are shared kernel
   state, not per-process app state; free() dispatches by address so it is
   free-safe).  Requires a C-linkage accessor into the kernel arena:
   core/fork_arena.cc exports fork_kernel_heap_push/pop, whitelisted in
   exported_symbols/osv_libsolaris.so.symbols so libsolaris.so can call them.

3. libsolaris.so writable statics (core/elf.cc + core/mmu.cc + include/osv/mmu.hh):
   ZFS globals live in libsolaris.so .data/.bss in the COW app slot:
   buf_hash_table (ARC hash), arc_anon/mru/mfu, the dbuf hash, arc_stats, ....
   A forked backend inserting an arc_buf_hdr into buf_hash_table.ht_table[]
   wrote its private COW copy; the AS0 txg-sync / dp_sync_taskq thread then read
   an empty table and NULL-dereferenced in buf_hash_remove (gdb: fault addr 0,
   arc.c:1137, dp_sync_taskq).  FIX: the ELF loader registers libsolaris.so's
   writable PT_LOAD segments; clone_address_space shares them verbatim (never
   COW) across every fork child.

4. large ZFS hash arrays (core/mempool.cc, mapped_malloc_large):
   buf_hash_table.ht_table and the dbuf hash are 8 MB vmem_zalloc arrays; >2 MB
   non-contiguous allocations bypass the arena AND the identity pool and land in
   the COW app mmap slot (verified: ht_table at 0x200000200040).  FIX: large
   allocations made under force_kernel_heap are registered fork-shared too.

Files (all gated #if CONF_fork):
  fs/vfs/kern_physio.cc                     +22   bio -> identity heap
  bsd/.../opensolaris_kmem.c                +52   SPL/ZFS heap -> identity heap
  core/fork_arena.cc                        +13   fork_kernel_heap_push/pop (C API)
  exported_symbols/osv_libsolaris.so.symbols +2   export those two symbols
  core/mmu.cc                               +40   fork_shared_module_ranges + share
  include/osv/mmu.hh                         +7   add_fork_shared_module_range decl
  core/elf.cc                               +18   register libsolaris.so wr segments
  core/mempool.cc                           +17   share large force-kernel-heap allocs

NEXT STEPS (the two remaining walls, precisely characterized)
================================================================================
(A) ZIL lwb sync-write completion.  The lwb write ZIO is issued
    (zil_lwb_write_issue -> zio_nowait) but never advances to WRITE_DONE while
    the block completion threads are idle.  Candidates: the lwb's root/write ZIO
    live in the page area (0x500..., identity/shared) yet the completion
    callback chain (zil_lwb_write_done -> zil_lwb_flush_vdevs_done ->
    zil_commit_waiter_done -> cv_broadcast(zcw_cv)) does not run -- suspect a
    lost taskq wakeup on the z_wr_int/z_wr_iss ZIO taskqs, or a bio completion
    whose zio_interrupt re-dispatch is dropped.  Next: instrument at the KERNEL
    biodone/req_done boundary (note: kprintf from a forked-child context does
    NOT reach the serial console once PG owns it -- verified; kernel-thread
    kprintf or a gdb-read counter is required), and inspect the z_wr_int
    taskqueue tq_queue depth vs the thread's sleep state to confirm/deny a lost
    taskqueue_enqueue wakeup.
(B) forked-backend writes generate no block I/O (DECISIVE new finding).  The
    virtio-blk write counter does not advance across `insert; checkpoint`, so
    the AS0 txg_sync_thread finds nothing to write for a forked backend's dirty
    data.  Next: trace the dirty-list linkage a forked backend appends to on
    dmu_write -- dnode_t.dn_dirty_link into objset os_dirty_dnodes (a multilist),
    objset into dsl_dataset ds_dirty_txg / dp_dirty_datasets (txg_list_t in
    dsl_pool) -- and confirm whether the LIST-HEAD writes are landing where the
    AS0 txg_sync walk reads.  All these container structs are now on the
    identity heap (fix #2), so the suspect is a multilist sublist head, a
    per-CPU/per-allocator index the child computes differently, or the txg the
    child's dmu_tx_assign lands in vs the txg AS0 syncs.  First isolate against
    RAMFS with THIS kernel to rule my changes in/out.

NO-REGRESSION / SCOPE

  byte-identical (the exported_symbols additions name symbols a conf_fork=0
  kernel does not define, which the version script simply omits -- harmless).

  shipped fixes rely on).
