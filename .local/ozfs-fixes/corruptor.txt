HEADLINE (honest)

* I did NOT land a fix this session.  OSv+PG is STILL NOT QUALIFIED at default
  recordsize=8k + 32G under KVM.  Do NOT relaunch the default-recordsize fleet.

* I DID make concrete forward progress and eliminate several hypotheses:
  - Built a FAITHFUL, layout-neutral reproducer and confirmed the residual
    corruptor reproduces reliably under pgbench -i -s1000 / -c16 RW at 8k+32G.
  - Proved it is NOT a forward tail-overflow of any ZFS kmem/kmem_cache object
    (an allocator-safe 16-byte trailing redzone on EVERY zfs_kmem_alloc /
    kmem_cache_alloc object -- abd_chunk, dbuf, arc_buf_hdr, zio_buf,
    dbuf_dirty_record, all of them -- checked at free NEVER tripped on the hot
    path; it only caught a self-inflicted instrumentation false positive, now
    understood and fixed: kmem_vasprintf allocated via libc vasprintf but was
    freed via kmem_strfree->zfs_kmem_free, so the redzone read past the libc
    allocation).
  - Proved it is NOT a per-CPU-area COW divergence across fork (percpu_base is
    aligned_alloc'd once in AS0 at boot -> identity heap -> coherent).
  - Proved it is NOT an aliasing bug in commit c6c89c59's large-alloc linear-map
    routing (free_page_ranges::alloc always returns a single VA-contiguous,
    non-overlapping page_range; the offset/header math round-trips correctly).
  - Confirmed the corruptor is a BROAD WILD-POINTER WRITE / USE-AFTER-FREE: it
    writes a (varying) pointer-sized value into whatever live object happens to
    occupy a semi-random heap address, so the FAULT always lands on a downstream
    victim, never the writer.  Captured 6 distinct downstream victims this
    session (all the SAME cause), see below.

* WHY I could not name the writer: every fault is a victim being *used* long
  after the wild write already succeeded to a valid-but-wrong address.  Neither
  a trailing redzone (catches only forward tail overflow), a poison-on-free /
  check-on-alloc UAF probe (defeated by OSv's shared per-size-class pool, which
  writes a freelist next-pointer into freed objects and hands a freed slot to
  ANY caller), nor a bounded quarantine (hung the guest / perturbed ARC) can see
  the writer.  Only a hardware watchpoint on a victim address BEFORE it is
  written will name it -- and victim addresses vary per run, so it needs an
  automated -smp1 watchpoint on a stable victim class (the recommended next
  step; I set up the infra but did not land it within the session budget).

CRITICAL LESSON (do not repeat my mistake): a redzone that ADDS bytes
(size+16) to every ZFS allocation changed the OSv pool SIZE CLASS of objects
that straddle the 1024-byte pool/page boundary (max_object_size = page_size/4 =
1024), which reshuffled the heap layout enough to MASK the corruptor -- a full
battery ran clean once on the +16 build and clean on reboot.  The un-padded
(faithful) build then corrupted 3/3.  Any instrumentation MUST be layout-neutral
(guard existing slack, or a side table) or it will mask this layout-sensitive
bug -- exactly like recordsize=32k and >=96G RAM mask it.

================================================================================
WHAT THE EVIDENCE NARROWS THE WRITER TO
================================================================================
* Scales with the count of small (8k) ZFS buffers (recordsize=32k => 4x fewer
  dbufs/abd_chunks/zio_bufs => survives) and with write concurrency; masked by
  >=96G RAM (little allocation/eviction churn -> window rarely hits).  The
  recordsize sensitivity points the WRITER at the ZFS 8k-record buffer
  alloc/free churn (dbuf / abd_chunk / arc_buf_hdr / zio / dirty-record
  lifecycle), NOT at fds, VMAs, or the scheduler (those are victims).
* It is an OVERFLOW-that-skips-my-guard OR (more likely) a USE-AFTER-FREE:
  a stale/dangling pointer into a ZFS buffer that was freed and whose slot was
  reused, written through after reuse.  The prior session already audited ZFS's
  own dbuf state machine (DB_CACHED => db_buf!=NULL is never violated by ZFS
  code) -> the db_buf clear is EXTERNAL, consistent with a wild write.
* It requires the fork COW boundary: a SINGLE forked backend + AS0 txg_sync is
  enough (pgbench -i, one COPY backend, sometimes corrupts), so it is not purely
  a multi-backend SMP race; it is the fork-child <-> AS0 interaction on the 8k
  ZFS buffer lifecycle.

tool that names the WRITER (all my content-guards only see victims):
  1. Instrument core/mempool.cc pool::add_page to log the header address of the
