destroy_address_space(child_as) EXACTLY ONCE  (the delicate invariant):
--------------------------------------------------------------------------
Two paths a fork child can take; the child AS must be destroyed once, never
zero (leak) or twice (double-free GP-fault / ~rwlock assert at reap).

The reap cleanup (libc/process/fork.cc) is guarded:
    if (child->address_space() == child_as) mmu::destroy_address_space(child_as);

PATH A - child exits normally (_exit / falls off end):
  thread never enters execve's AS switch; child->address_space() stays == child_as
  => reap cleanup destroys it.  ONCE.  (counter dec once.)

PATH B - child execs (fork+execve):
  a0e9's execve destroyed child_as INLINE while still on the child's stack -- fine
  for the old malloc'd/biased stack, but FATAL for same-VA (that stack IS the
  child AS's private page; freeing it pulls the rug, and reloading CR3 to AS0
  aliases the parent's page).  My execve instead:
    1. pre-check target exists (access F_OK) so a failed exec returns -1 to caller;
    2. set_address_space(AS0);
    3. rsp-switch onto the thread's OWN kernel stack (global-heap, valid in every AS);
    4. on that kernel stack: switch_to_runtime_page_tables() (CR3=AS0), THEN
       mmu::destroy_address_space(s_old_as)  <-- destroys child_as HERE, ONCE,
       safely (no longer running on the child's app stack);
    5. run the target, join, _exit.
  Because step 2 set child->address_space()=AS0, the later reap cleanup sees
  AS0 != child_as and SKIPS its destroy.  => destroyed ONCE by execve.  (counter
  dec once.)  No leak, no double-free.

  [The bug the merge would have reintroduced without this fix: my original
  execve set AS0 but deferred destroy to the reaper; combined with a0e9's guard
  (AS0 != child_as -> skip) the AS would have LEAKED on every fork+exec.  Fixed
  by destroying in execve on the kernel stack, matching the guard's design.]
