  It is NOT the latch self-pipe and NOT the WaitEventSet epoll.  It is the
  child-exit -> parent SIGCHLD.  When PostgreSQL's startup process (pid 593, a
  fork child) finishes crash recovery and EXITS, OSv fork emulation
  (libc/process/fork.cc child_exited(), line 461) synthesizes the parent
  notification with kill(getpid(), SIGCHLD).  The postmaster's process-level
  SIGCHLD reaper MUST run in AS0 (the top-level app globals), which is exactly
  what the base kill() does for a self-signal (target_as stays nullptr -> AS0).
  K1's `else if (pid == getpid()) target_as = current_address_space()` routes
  that reaper into 593's DYING COW child address space instead.  Running the
  postmaster reaper against the child's half-torn-down COW mapping faults at the

  postmaster never observes the startup process finished -> it never launches
  checkpointer/bgwriter, never reaches "ready to accept connections", and the
  two already-forked backends (591 latch-wait 300s, 592 re-loop) wait forever
  for a startup handshake that is stuck.  => a LOST child->parent SIGCHLD.
