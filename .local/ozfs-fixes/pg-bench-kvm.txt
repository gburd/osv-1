STABILITY FINDING (decisive) -- OSv-KVM under concurrent write load
================================================================================
The OSv guest CRASHES during the HammerDB TPROC-C 500-warehouse SCHEMA BUILD,
at BOTH 32 and 8 concurrent loaders, within ~1-2 min. TWO crash signatures, same
class (cross-AS free in a kernel worker thread, faulting in an atomic context):

 (A) Assertion failed: ef->rflags & processor::rflags_if (arch/x64/mmu.cc:
     page_fault:39)  RIP -> sbcompress (bsd/sys/kern/uipc_sockbuf.cc:840)
     = page fault with interrupts disabled in the socket-buffer compaction path.

 (B) Assertion failed: sched::preemptable() (arch/x64/mmu.cc: page_fault:38)
     backtrace: memory::pool::free <- <ZFS callback> <- taskqueue_run_locked
     (subr_taskqueue.c:327) <- taskqueue_thread_loop (subr_taskqueue.c:498)
     = the BSD/ZFS taskqueue worker (AS0) frees memory a forked backend
       allocated in its COW-private arena -> touches a diverged/unmapped page
       while preemption is disabled -> illegal fault -> abort.

 Consequence: NOT a clean stop -- it left on-disk system-catalog corruption:
     ERROR: index "pg_database_oid_index" contains unexpected zero page at
     block 0 (torn write from the crash). Pool rebuild required to recover.

BUT: plain OLTP transaction load is STABLE. pgbench TPC-B from the external
driver, cross-instance, survives cleanly with ZERO failed transactions and no
crash at EVERY concurrency tried (fresh clean raidz, sync=standard, smp32/32G):
     -c 1  -T30 : 10546 tx, 0 failed, 353 tps
     -c 4  -T30 : 31067 tx, 0 failed, 1059 tps
     -c 8  -T30 : 45880 tx, 0 failed, 1599 tps
     -c 16 -T30 : 59513 tx, 0 failed, 2180 tps
     -c 32 -T30 : 63479 tx, 0 failed, 2579 tps   (guest alive, 0 crashes)
 (loopback-vs-network note: this is REAL cross-instance TCP over the tap NIC +
  ENI DNAT, driver on a separate c5.4xlarge -- not hostfwd loopback.)

INTERPRETATION: OSv-KVM stock PG18 is stable for concurrent OLTP small-txn load
over the network on the durable raidz, but the HammerDB schema BUILD's bulk
COPY + concurrent index-create pattern drives enough ZFS-taskqueue/socket-buffer
kernel free traffic to hit the forked-backend cross-AS COW free fault. The wall
is in the DATA-LOAD path, not the steady OLTP path. Next: try to get the schema
built with a single loader (minimal concurrent taskqueue pressure) so the
TPROC-C RUN (which is small-txn OLTP, like pgbench) can be measured.
