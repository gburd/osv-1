DECISIVE NEW EVIDENCE (what it rules the writer IN / OUT of)
================================================================================
1. NOT an in-flight DMA modification of the ZFS data buffer.
   Ran the prior agent's WALL3TORN probe (patch_torn.py): in vdev_disk_io_done
   -> abd_return_buf, unconditionally abd_cmp_buf(abd, buf, n) for scatter ABDs
   (the 8k write buffer).  It NEVER fired (0 hits) across a full corrupting -i.
   => the scatter data ABD is byte-identical from io_start (borrow+copy) to
   io_done (DMA complete).  The data buffer is NOT scribbled during its write.

2. Corruption is ON DISK (persists across re-read) yet the DMA'd buffer was
   clean (from #1) => the on-disk block does not match what a clean data ABD
   would have produced.  Combined with the ~128 KiB-aligned corruption unit
   (signature B) and the "reads the wrong data" nature, this points the writer
   at ZFS METADATA in the identity heap -- an indirect block / blkptr / dnode
   dbuf -- clobbered by a wild pointer write, so ZFS later reads the wrong
   physical location (or a stale/short block) and fails checksum / returns
   garbage.  The victim breadth (data blocks, PT pages, entropy ring, wait
   records, scheduler state) is exactly a wild pointer scribbling semi-random
   valid-but-wrong addresses.

3. Independent of: ZIL (sync=disabled still corrupts), compression (off ->
   invalid-page instead of EIO, same corruption), and parallel query / DSM
   (max_parallel_workers=0 and max_parallel_maintenance_workers=0 still corrupt
   -- the "parallel worker" in some errors is incidental).  A SINGLE COPY
   backend + AS0 txg_sync is sufficient.

4. Substantially an SMP race (reliable at -smp4, marginal at -smp1; see above).

5. The lazy-TLB-flush optimization is NOT the bug.  A/B: forced flush_tlb_all()
   to IPI ALL CPUs (removed the app_thread/lazy_flush_tlb skip in
   arch/x64/mmu.cc); rebuilt; -smp4 -i still EIO'd.  Reverted.

RECOMMENDED NEXT STEP (the definitive one, revised)
================================================================================
The writer is a WILD POINTER WRITE that (per evidence #1/#2) lands on ZFS
METADATA (indirect block / blkptr / dnode dbuf) or page-table pages in the
identity heap, NOT on the in-flight data ABD.  Victim-chasing and single-8-byte
watchpoints have failed twice.  Two layout-neutral options that NAME it:

  (a) METADATA CANARY (preferred, cheap, deterministic-ish):
      In the zio WRITE pipeline, right after zio_checksum_generate() computes a
      block's checksum, stash (blkptr DVA -> 64-bit fletcher of the ABD) in a
      fixed identity-heap side table.  Right before vdev_disk_io_start() DMAs
      that block, recompute and compare.  A mismatch proves the buffer changed
      between checksum and DMA and dumps the DVA + a backtrace.  ALSO stash the
      dbuf/dnode/indirect addresses and background-checksum them; on mismatch
      dump the victim ADDRESS (stable in the identity heap) -> then re-run with
      a KVM hardware write-watchpoint on THAT address (DR0-3, honored under KVM)
      to catch the writer's PC.  Layout-neutral (side table, no object resize --
      byte-adding instrumentation MASKS this bug, confirmed again this session).

  (b) PAGE-TABLE-PAGE canary: signature (D) shows a shared kernel PTE/PT page
      got clobbered.  Checksum AS0's kernel PT pages (or watch a specific
      long-lived kernel PDPT/PD page) in a background sweep; first mismatch =>
      victim address => hardware watchpoint => writer PC.

Then classify the named writer:
  OSv ZFS platform layer (arc_os/abd_os/dbuf/zio glue) -> [#1423/OpenZFS];
  OSv-fork interaction (clone/teardown/COW/PT)         -> [fork-stack/CONF_fork].
