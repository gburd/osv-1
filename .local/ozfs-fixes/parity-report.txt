*** THE PARITY STORY (honest, one paragraph) ***
At LOW concurrency OSv-KVM matches Linux: single-client RW is actually FASTER on
OSv (270 vs 233 tps at 8k; the musl PG + OSv thread model has lower per-op
overhead), and c8 is within 3% (1,756 vs 1,801). recordsize barely moves pgbench
on either side (SLOG absorbs the sync write) -- exactly the prior finding. BUT
OSv PLATEAUS/REGRESSES past ~c16 on the write path (c64: 2,750 vs Linux 18,876,
~7x lower) and past ~c8 on the read path (RO c32: 22k vs 204k). This is the
fork_arena thread-backed backend model: OSv runs every PG backend as a thread in
one address space; beyond ~16 concurrent write backends the scheduler + shared
allocator serialize, while Linux's process-per-backend scales near-linearly. So:
OSv+PG on ZFS is PRODUCTION-VIABLE for low-to-moderate concurrency (<=16 clients)
with parity-or-better single-client latency, and is CONCURRENCY-LIMITED above
that. The bulk-load path is at parity: pgbench -i -s300 (30GB) loaded in 40.4s
on OSv-KVM vs 40.7s on Linux -- IDENTICAL.

*** HammerDB TPROC-C ON OSv -- BLOCKED by a backend crash (honest FAIL) ***
================================================================================
HammerDB TPROC-C could NOT be run on OSv (KVM). The 250-warehouse schema BUILD
and the TPROC-C run both CRASH the guest under sustained heavy multi-backend
write / stored-procedure load. Two distinct crash signatures, both in the
OSv fork/mmap coherence family (NOT a harness bug, NOT DROP DATABASE):

  (1) SCHEMA BUILD (bulk COPY, 4-16 concurrent loaders): guest aborts with
      page_fault -> mmu::vm_fault -> osv::handle_mmap_fault
      Client sees: "error writing pgsqlNN: input/output error" (the EIO facet)
      as the connection dies when the guest crashes mid-write. Reproduced at
      both VU_BUILD=16 (mid-build) and VU_BUILD=4 (later in build). A small
      10-warehouse build (VU_BUILD=2) COMPLETED clean -- so it is a sustained-
      write-pressure threshold, not a hard block on all HammerDB.
  (2) TPROC-C RUN (stored procedures, VU>=4): guest aborts with
      page_fault -> elf::program::lookup -> elf::object::resolve_pltgot ->
      elf_resolve_pltgot   (a null-page fault during LAZY PLT symbol resolution
      in a forked backend). Client sees "Connection to database failed" for all
      VUs as the guest dies.

  Both are the SAME lost-wakeup / COW-address-space-coherence class as the
  documented startup-handoff wall and the ProcSignalBarrier hang -- here it
  manifests as an mmap/PLT-resolution fault when many forked backends do heavy
  work simultaneously. The pgbench path avoids it (simple query protocol, no
  stored procs, pre-resolved code paths, and it plateaus in throughput before
  reaching the crash pressure). So:
    - OSv HammerDB TPROC-C NOPM: NO valid median rows (would be crash datapoints).
    - NOT faked. A 10-ware build proved the schema builds; the RUN crashes at
      the PLT-resolution path, so no NOPM was produced.
    - The Linux HammerDB NOPM baseline IS complete and banked (above).

  This is a NEW finding beyond the DROP-DATABASE ProcSignalBarrier bug: even
  DROP-DATABASE-free, sustained heavy concurrent forked-backend work crashes the
  current image. Route to the same fork-coherence fix track. It does NOT affect
  the pgbench parity numbers (which completed 0-failed).

KNOWN LIMITATION (does NOT affect the OLTP numbers above)
================================================================================
DROP DATABASE / DROP TABLESPACE / any ProcSignalBarrier op HANGS on OSv
(documented open bug, deferred to a scheduler-facet fix). The harness NEVER
issued DROP DATABASE: each recordsize cell was seeded by streaming a PRISTINE
initdb cluster onto a FRESH raidz pool via cpiod (no drop+recreate). pgbench
loads into the pristine `postgres` DB; the bench DBs are created via CREATE
DATABASE on a pristine cluster (no prior drop). The parity numbers are fully
valid without DROP DATABASE.

MUSL LOCALE (harness detail, solved): musl PG on OSv has no "C.UTF-8" libc
locale data. A libc-provider database created as C.UTF-8 (the driver's default
LANG) is created OK but is UN-CONNECTABLE ("could not create locale C.UTF-8:
ENOENT"). SOLVED by (a) booting the guest with --env=LC_ALL=C and (b) creating
bench DBs with LOCALE_PROVIDER builtin BUILTIN_LOCALE 'C', which is connectable
because the builtin provider needs no libc locale data. pgbench uses the
pristine `postgres` DB (already pure C) and is unaffected.

TRANSIENT CRASH: one early CREATE DATABASE sequence tripped a one-off null-page
fault that recovered cleanly on reboot (WAL redo). Noted as intermittent, same
fork-coherence family.
