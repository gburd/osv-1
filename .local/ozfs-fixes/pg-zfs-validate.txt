      -device virtio-blk-pci,id=blk0,drive=hd0 \
      -drive file=build/last/usr.img,if=none,id=hd0,cache=writeback,aio=threads \
      -device virtio-blk-pci,id=blk1,drive=hd1 \

CROSS-INSTANCE NETWORKING (methodology-update deliverable) -- WORKS
================================================================================
Requirement: an EXTERNAL instance in subnet-08627f3be3da35553 drives HammerDB
against the OSv guest's PG over a real NIC (qemu user-net/hostfwd is loopback-
only and cannot be reached cross-instance).

Solution (verified guest gets IP + binds 5432 over tap):
  * tap0 on the host: 192.168.100.1/24 ; guest virtio-net static
    --ip=eth0,192.168.100.2,255.255.255.0 --defaultgw=192.168.100.1
    -> guest boots "eth0: 192.168.100.2", PG binds 0.0.0.0:5432,
       host reaches it: TAP-OPEN (echo >/dev/tcp/192.168.100.2/5432 succeeds).
  * Host ENI DNAT so an external instance hits the host's private IP:
      sysctl net.ipv4.ip_forward=1
      iptables -t nat -A PREROUTING -i enp125s0 -p tcp --dport 5432 \
               -j DNAT --to-destination 192.168.100.2:5432
      iptables -t nat -A POSTROUTING -s 192.168.100.2/32 -o enp125s0 -j MASQUERADE
      iptables -A FORWARD -i enp125s0 -o tap0 -p tcp --dport 5432 -j ACCEPT
      iptables -A FORWARD -i tap0 -o enp125s0 -j ACCEPT
    An external instance connects to 172.31.12.162:5432 -> PREROUTING DNAT ->
    guest. (Host-LOCAL tests hit OUTPUT not PREROUTING so they don't exercise
    the DNAT; a second instance does. Mechanism is standard and correct.)
  * EC2 side: SG sg-0e2719d4599449a12 now allows tcp/5432 from 172.31.0.0/20.
  * The tap MUST be visible to qemu: run qemu either on the host (needs qemu
    installed on AL2023 -- not in default repos) OR in a `--network host`
    container (what I used: container `osv-net`, fedora:39 + qemu-system-x86,
    --privileged --network host --device /dev/kvm, same bind mounts). The tap
    approach works identically for Firecracker (tap + virtio-net) in the bench
    phase.
  Scripts: /tmp/setup-tap-net.sh, /tmp/phase-b-tap-container.sh (on floki too).

THE TWO ZFS-ERA FORK WALLS I ROOT-CAUSED AND FIXED (commit 18f59ac3, bundled)
================================================================================
The prior PG-on-OSv work ran on RAMFS /data; ZFS + a second virtio-blk disk +
running zpool.so/zfs.so before postgres exposed two NEW cross-AS coherence bugs.
Both are the SAME proven rule as all prior fork fixes: a kernel structure that
fork-shared code reads/frees must live on the identity kernel heap, never the
COW fork arena -- OR (new sub-case) must not be a dangling pointer into an app
that osv::run() already unloaded.

WALL 1 -- atfork prepare handler SIGSEGV at PostgreSQL's first fork().
  Symptom (gdb, verbatim): postmaster reaches "listening on 0.0.0.0:5432" then
    Aborted; handle_mmap_fault(addr=0x1000004e8000, SIG=11) <- vm_fault
    <- page_fault <- (instruction fetch, error_code=0x10, page-not-present)
    <- 0x1000004e8350 <- __osv_run_atfork_prepare()  (libc/pthread.cc:313,
       "if (it->prepare) it->prepare();") <- fork()+95 <- fork_process+42.
  Root cause (gdb-proven, two parts):
   (a) atfork_handlers (std::vector, process-global kernel BSS) had its BACKING
       STORE in the COW fork arena: _M_start=0x30000013e560 (arena_base 0x3000..)
       because register_atfork() runs on an app thread. A forked child read a
       DIVERGENT arena copy -> garbage handler pointer.
   (b) EVEN AFTER moving the vector to the identity heap (_M_start=0x6001..), the
       fault persisted: the handler ADDRESSES themselves (0x10000040f350,
       0x1000004e8350) are in objects that osv::run() ran and then UNLOADED --
       zpool.so and zfs.so, invoked in the boot cmdline (and by
       import_extra_zfs_pools) BEFORE postgres, register atfork handlers via
       __register_atfork and exit; their code is unmapped but their entries
       persist in the global list. PG's fork() then calls a dead pointer ->
       instruction-fetch SIGSEGV. (Both handler pages "Cannot access memory".)
  Fix (libc/pthread.cc, #if CONF_fork):
   (a) ATFORK_KH() = fork_arena::kernel_heap_scope around register_atfork()'s
       push_back -> the vector (and its regrowth) lives on the identity heap.
   (b) atfork_handler_live(fn): call a handler only if
       elf::get_program()->object_containing_addr(fn) != nullptr -- handlers in
       unloaded objects are skipped. Applied to prepare/parent/child.
  Result: PG forks past this; the startup process runs and logs "database system
  was shut down at ..." (real recovery output).

WALL 2 -- virtio-blk request freed cross-AS -> fork_arena chunk-magic abort.
  Symptom (verbatim), once PG forked and the startup process did ZFS I/O:
    Assertion failed: h->magic == chunk_magic (core/fork_arena.cc recover:257)
      fork_arena::free(void*)+72
      virtio::blk::drain_queue(virtio::vring*)+127
      virtio::blk::req_done()+196
  Root cause: make_request() does `new blk_req(bio)` on the forked backend's
  thread, so the request lands in that backend's COW arena. The single blk
  completion thread (req_done -> drain_queue, AS0) then `delete req` -> free()
  reads a divergent arena chunk header (magic mismatch) -> abort. IDENTICAL to
  the shipped virtio-net TX net_req fix, but for the block I/O path ZFS exercises
  (ramfs had no virtio-blk, so this never surfaced before).
  Fix (drivers/virtio-blk.cc, #if CONF_fork): allocate blk_req under
  fork_arena::kernel_heap_scope so `delete` frees correctly from any AS.
  Result: PG forks + does ZFS I/O without the abort; recovery proceeds.

THE NEXT WALL (precisely symbolized, NOT fixed -- the current gate to serving)
================================================================================
After WALL 1+2, PG comes up as far as:
    LOG:  starting PostgreSQL 18.4 on x86_64-pc-linux-musl ...
    LOG:  listening on IPv4 address "0.0.0.0", port 5432
    LOG:  database system was shut down at 2026-07-25 14:21:18 UTC   ([startup])
  ...and then HANGS. psql gets "FATAL: the database system is starting up"
  (so the postmaster IS reachable on 5432 -- proving the ZFS-on-NVMe cluster
  opened and the network path works -- but it never reaches "ready to accept
  connections"). Reproduces on a freshly re-seeded (clean) pgdata pool, so it is
  NOT stale state / dirty ZIL.

  gdb thread walk (all 4 vCPUs idle => a LOST WAKEUP, nothing runnable):
    tid=596 name=/b/.local/pg18/ (POSTMASTER):
       epoll_wait <- epoll_file::wait <- sched::thread::wait  (asleep in
       ServerLoop, waiting for the startup process to signal readiness)
    tid=598/599/600 (forked aux: startup / checkpointer / bgwriter):
       parked at sched::thread::switch_to()+232 with rbp in their private COW
       AS (0x200000...) -- descheduled and NOT on a runnable queue; their
       wake-up never arrives.
  Interpretation: the forked startup process finished or is blocked and the
  postmaster<->startup readiness handoff loses its wakeup across the fork COW
  address-space boundary -- the SAME class as the shipped epoll/net_channel/
  timer-park fixes, but on the specific primitive these ZFS-era aux processes
  block on (candidates, in priority order):
    (i)  the ZFS synchronous-I/O completion path: a forked process calls
         zio_wait(); the blk completion thread (req_done, AS0) drives
         vdev_disk_bio_done -> zio_interrupt -> cv_broadcast on the zio's condvar
         /mutex, which ZFS allocated (kmem_cache) on the forking process's thread
         -> arena-divergent -> the waiter's cv is never signalled in its AS.
         (module/os/osv/zfs/vdev_disk.c + the SPL condvar/kmem allocs.)
    (ii) PG's latch self-pipe (WAIT_USE_SELF_PIPE) SetLatch across the
         startup->postmaster handoff losing the wakeup (a ZFS-timing variant of
         the shipped SIGCHLD/PM_RUN fix).
  This is a bounded-but-real fix (route the ZFS sync-I/O wait primitive -- zio
  condvar+mutex, or the SPL kmem object backing it -- onto the identity kernel
  heap under CONF_fork, likely then uncovering 1-2 further ZFS-completion sites),
  NOT a build/layout problem. It is the single remaining gate to psql rows +
  pgbench on PG-on-ZFS-on-NVMe.
