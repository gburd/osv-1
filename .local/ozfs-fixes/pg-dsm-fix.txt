VERDICT (one line)
================================================================================
The handed-off DSM ENOENT wall is cause (i) exactly as predicted: a shared
registry whose NODES landed in per-AS COW arena memory.  Every fix in this
report is the SAME proven pattern -- force a fork-shared kernel structure onto
the identity kernel heap (kernel_heap_scope) so it is byte-identical in every
address space, never a COW-private arena copy.  Four distinct structures needed
it to get from "ready to accept connections" to a served query; a fifth
(fork+reap lifecycle) is the next wall and is precisely symbolized but NOT fixed
here.

================================================================================
THE gdb / analysis FINDING (which cause -- proven, not inferred)
================================================================================
Cause (i) confirmed.  PG's DSM POSIX backend (src/backend/storage/ipc/
dsm_impl.c dsm_impl_posix):
    flags = O_RDWR | (op == DSM_OP_CREATE ? O_CREAT | O_EXCL : 0);
    fd = shm_open(name, flags, PG_FILE_MODE_OWNER);
dsm_postmaster_startup() CREATES the control segment in the postmaster at boot;
dsm_backend_startup() ATTACHES it by name in EVERY forked backend during
InitPostgres.  OSv keeps named segments in a kernel-static registry
(libc/shm.cc: posix_shm_objects, std::unordered_map<string,fileref>).  The map
OBJECT lives in shared kernel BSS, but its NODES / bucket array / std::string
keys / fileref control blocks are heap-allocated -- and an APP thread's malloc
routes to the COW fork arena (VA 0x3000..), so every process gets a divergent
PRIVATE copy of the map contents.  A name inserted by process A is invisible to
process B -> shm_open(name, O_RDWR) returns ENOENT ("could not open shared
memory segment").  shm_file::_pages (the physical huge-page map that gives
MAP_SHARED its cross-fork coherence) had the identical gap.

Note on the create-BEFORE-fork subtlety: because the postmaster CREATES the DSM
control segment before it forks any backend, a naive create-then-fork test still
passes even WITHOUT the registry fix (the child COW-inherits the parent's arena
snapshot including that node).  The registry-node fix is still correct and
required (a segment created by a backend and attached by a sibling/parallel
worker, or any re-creation after the first fork, diverges); the fix is byte-
identical when the creator forks first and load-bearing when it does not.

THE FIXES (minimal, correct, #if CONF_fork; non-fork byte-identical) -- e35d04172
================================================================================
Every change routes a fork-shared kernel structure onto the identity kernel
heap via fork_arena::kernel_heap_scope, gated #if CONF_fork.  In the conf_fork=0
build the guards vanish and the two helper macros expand to `do {} while (0)` --
compiled and verified byte-identical (conf_fork=0 build: all changed .o compile,
loader.elf links).

1. libc/shm.cc  -- THE DSM ENOENT FIX.
   SHM_REGISTRY_KH (kernel_heap_scope) around every mutation of the POSIX/SysV
   registries: shm_open (posix_shm_objects insert + the make_file), shmget
   (shmkeys), shmat (shmmap).  So the map nodes / string keys / fileref control
   blocks live on the identity heap and all processes share ONE registry.

2. core/mmu.cc  -- shm_file::_pages coherence + post-fork mmap vmas.
   (a) shm_file::page(): the _pages node (physical huge-page map) onto the
       identity heap, so every AS faulting the same MAP_SHARED offset gets the
       SAME physical page (not a divergent per-AS page).
   (b) map_file() and map_anon(): the vma object (+ its map_file_page_* page
       allocator) onto the identity heap.  A fork child's post-fork mmap vma is
       disposed CROSS-AS by destroy_address_space() on the REAPER (AS0); an
       arena-resident vma's VA is unmapped there -> null-deref in
       clear_and_dispose.  (Caught first: the DSM regression test's child mmap'd
       shm then exited -> reaper fault at destroy_address_space+709.)

3. fs/ramfs/ramfs_vnops.cc  -- THE ramfs READ-ASSERT FIX.
   kernel_heap_scope in ramfs_enlarge_data_buffer: the segment DATA buffer and
   the segment-map node onto the identity heap.  A backend reading a ramfs file
   the postmaster grew otherwise saw a divergent/empty segment map ->
   ramfs_read_or_write_file_data's uio_offset bounds assertion (ramfs_vnops.cc:
   465).

4. core/net_channel.cc  -- THE net-RX preemptable-assert + sbdrop FIXES.
   NET_SHARED_KH in add_poller/del_poller/add_epoll/del_epoll and
   classifier::add: the RCU poller vectors / epoll-set nodes / channel hashtable
   nodes onto the identity heap.  Populated by a backend adding its socket to
   epoll, but WALKED by the virtio-net RX path (net_channel::wake_pollers,
   classifier::post_packet) in a kernel thread / IRQ context (AS0, preemption
   off) -> arena VAs unmapped there -> "Assertion failed: sched::preemptable()
   (page_fault)".

5. bsd/porting/uma_stub.cc  -- THE sbdrop-panic FIX (mbufs).
   kernel_heap_scope around uma_zalloc_arg's slab malloc/alloc_page.  UMA backs
   the whole BSD net stack (mbufs, clusters).  A backend allocates a SEND-path
   mbuf for its query response; the RX/timer thread later drops it
   (net_channel::process_queue -> tcp_input -> sbdrop).  An arena mbuf makes the
   socket send-buffer chain inconsistent across AS (sb_cc disagrees with the
   chain) -> panic("sbdrop") (uipc_sockbuf.cc:924).

6. arch/x64/arch-switch.hh  -- THE thread-teardown fault FIX.
   kernel_heap_scope around init_stack()'s kernel-stack malloc (it was the ONE
   thread allocation not already scoped; the TCB/TLS and syscall stacks right
   below it already were).  A forked backend otherwise ran on an ARENA kernel
   stack that the reaper frees from AS0 in ~thread -> stack.deleter ->
   free(begin) on an arena VA (0x3000..) -> page fault in ~thread (caught in the
   concurrent run: ~thread()+1454, RDI=0x30000000..).

THE REGRESSION TEST -- tests/tst-fork-posix-shm.cc (author Greg Burd)
================================================================================
Registered in modules/tests/Makefile.  Mirrors PG's DSM create/attach handoff:
  parent (proc A) shm_open(O_CREAT|O_EXCL)+ftruncate+mmap(MAP_SHARED), writes a
    magic value, closes the create fd (name persists, like PG);
  fork();
  the CHILD (proc B) shm_open(same name, O_RDWR)+mmap(MAP_SHARED) and:
    (1) must NOT get ENOENT (the DSM attach wall),
    (2) must read the parent's pre-fork value (create/attach coherence),
    (3) writes a value the PARENT must then observe (MAP_SHARED write-back,
        which PG relies on -- barrier-synchronized).
The CHILD owns the verdict (like a real PG backend), sidestepping OSv fork
exit-status plumbing.  Uses -smp 2 (fork needs >=2 vCPUs on this build).

  On the arena-node path (registry fix reverted in shm_open): reproduced the
  child mmap'ing shm then exiting -> reaper fault at destroy_address_space+709
  (that surfaced fix 2b).  With all fixes: PASS.
  KVM -smp 2, final:
    parent created "/tst-fork-posix-shm.seg", wrote parent_val=0xc0ffee1234567890
    PASS: forked backend attached by name (no ENOENT), read
          parent_val=0xc0ffee1234567890, wrote child_val=0xbadc0de0feedface at
          0x200000301000
    parent: after wait child_wrote=1 child_val=0xbadc0de0feedface (A=0x200000201000)
    PASS: parent observed child's MAP_SHARED write child_val=0xbadc0de0feedface
          -- POSIX shm coherent across fork
  (child at VA 0x200000301000, parent at 0x200000201000 -- different VAs, SAME
   physical page: genuine cross-fork POSIX-shm coherence.)

NEXT WALL (distinct, precisely symbolized, NOT fixed here -- honest)
================================================================================
FORK+REAP LIFECYCLE, after ~2 forked backends complete and are reaped:
  general protection fault
    osv::application::get_current()+287        (runtime->app.get_shared())
    sched::thread::thread(...)+548             (ctor: _app_runtime = app->runtime())
    fork_thread(...)+552
    fork+117
The next backend's fork() -> new thread ctor -> application::get_current()
dereferences a CORRUPT _app_runtime (the forking thread's shared_ptr control
pointer is garbage).  Deterministic: the 1st and 2nd forked backends serve real
rows; the 3rd trips this.  Under KVM it escalates to abort("exception nested too
deeply"); an early TCG boot variant surfaced the same class as
"reschedule_from_interrupt: exception_depth <= 1".  The thread OBJECT,
_detached_state, _tls and now the kernel stack are all identity-heap, so this is
a subtler accumulation across fork/reap cycles (candidate: the application_
runtime shared_ptr refcount seen across a torn-down child AS, or an address_
space* reuse feeding fork_arena::slot_for after release_as).  It does NOT block
the FIRST query (or the first two, or 3 concurrent) -- it is the sustained-
serving wall, a separate investigation from the DSM milestone.

Do NOT read this as "PG is production-ready": it is not; sustained sequential
connections trip the lifecycle wall.  But the milestone asked for -- the first
stock-PG query on OSv -- IS served, with the verbatim rows above.

the SAME rule as the shipped struct-file / signal-table / thread-object / arena-
