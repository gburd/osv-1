--------------------------------------------------------------------------------
3. Bug B -- ROOT CAUSE (live gdb, HEAD, fresh single-file, -smp4)
--------------------------------------------------------------------------------
At the wedge: postmaster (thread 653) idle in epoll_file::wait (ServerLoop,
correct); two PG children (655, 656) parked in sched::thread::switch_to and
never rescheduled; their stacks live in a fork-child COW AS (addrs 0x6001....).
Reading thread 655's kernel-stack return addresses (addr2line via loader.elf),
top-down = call order:

  sigprocmask(int, sigset_t const*, sigset_t*)+283        <- PG child masks signals
   -> osv::unwait_for_signal(sched::thread*, unsigned)+246
      -> osv::waiters+1512                                 <- global waiters list (waiters_mutex)
         -> malloc(size_t)+63                              <- allocate a std::list node
            -> std_malloc(size_t, size_t)+157
               -> memory::pool::alloc()+164                <- pool slow path
                  -> mmu::file_vma::file_vma(addr_range,..,intrusive_ptr<file>,..)+181
                     -> vfs_file::stat(stat*)+52
                        -> vn_lock(vnode*)+33
                           -> memory::pool::alloc()+164     <- RE-ENTERS the allocator
                              -> mmu::file_vma+181          <- recursion continues
                                 -> ... (repeats; multiple pool::alloc / file_vma frames)

This is the SAME signature-F allocator-recursion family that F2a/F2b addressed,
but at a DIFFERENT alloc site than c8f9c82b's coherent_wait_record fix covered:
here the recursion is the std::list-node allocation inside osv::unwait_for_signal
(under waiters_mutex), whose pool::alloc slow path constructs a file-backed
mmu::file_vma (a new pool page), whose vnode-lock/stat path re-enters
pool::alloc. Manifests as a plain hang (no assert), matching the dropdb report's
"plain hang" variant of Bug B.

WHY the DROP DATABASE commit triggers it: the commit changes libc/signal.cc
kill() so a self-signal (pid==getpid()) now runs its handler in the CALLER's own
COW address space (target_as = current_address_space()) instead of AS0. During
PG startup the children self-signal (sigprocmask / latch machinery is exercised
before "ready"); routing those self-signals through the fork-child-AS wait path
(osv::waiters / unwait_for_signal) is what drags startup into the file_vma-under-
waiters_mutex allocation that recurses. On c8f9c82b those startup self-signals
took the AS0 path and never hit this allocation, so it booted clean. The fix's
own comment asserts "the branch NEVER fires during startup" -- the fresh-pool
A/B contradicts that: the branch (or its downstream AS-routed handler thread) is
what perturbs startup enough to expose the waiters_mutex allocator recursion.

--------------------------------------------------------------------------------
4. THE TRADEOFF (why "just keep the fix" is not viable as-is)
--------------------------------------------------------------------------------
To document the bug the fix targets, I booted the c8 loader (no fix) via osv-net
(host netns, tap0) so an external psql could reach the guest, on a fresh raidz:
  external psql (osv-net fedora psql 15.6) -> guest 192.168.100.2:5432
  inet_server_addr = 192.168.100.2, banner = PostgreSQL 18.4 on x86_64-pc-linux-musl
  CREATE DATABASE x TEMPLATE template0;   -> "CREATE DATABASE", rc=0
  DROP DATABASE x;                          -> HANGS (psql timed out at 50s, rc=124)
So on c8 the DROP DATABASE wedge is REAL and reproduces -- that is the bug the
fix was written for. But the fix, as landed, wedges startup (Bug B), so:
  * HEAD (fix on):  PG never reaches ready -> cannot even attempt DROP DATABASE.
  * c8  (fix off):  PG reaches ready, but DROP DATABASE hangs.
The fix swaps a "hangs on DROP DATABASE" bug for a "hangs on every startup" bug.

--------------------------------------------------------------------------------
5. PROPOSED NEXT STEPS + PR CLASSIFICATION (no blind landing)
--------------------------------------------------------------------------------
Bug B  [fork-stack]  -- the actionable one.
  Root: std::list-node allocation inside osv::unwait_for_signal under
  waiters_mutex whose pool::alloc slow path builds a file_vma that re-enters
  pool::alloc. Fix should mirror F2b's approach: keep the wait path ALLOCATION-
  FREE. Options, in order of laziness:
    (a) Narrow the 3fcc23b36 kill() change so the self-signal AS-routing does
        NOT apply during PG startup / to the postmaster's own startup children
        (only DROP DATABASE / DROP TABLESPACE need it, which run post-ready).
        i.e. gate the new branch so it cannot perturb the startup self-signals.
    (b) Pre-reserve the osv::waiters list node per-thread (like F2b's per-thread
        coherent wait_record slots) so unwait_for_signal never mallocs under
        waiters_mutex. This is the general fix and also hardens the wait path.
  Recommendation: REVERT or gate 3fcc23b36 until (a)/(b) lands, because as-is it
  regresses boot for the whole benchmark fleet. The DROP DATABASE wedge is the
  lesser evil (post-ready, one command) vs 0% boot success.

Bug A  [pool-state, likely OpenZFS/#1423-adjacent or an OSv VFS mount edge] --
  NOT a fresh-pool bug; 0/10 on fresh raidz. It is a dirty/half-imported raidz
  artifact. If it must be chased, reproduce by hard-killing a serving raidz guest
  mid-write (dirty the pool) then `import -f` + `zfs mount`, and gdb the wild
  deref in the ZFS VFS_MOUNT op. Low priority for the benchmark if the harness
  keeps pool hygiene (fresh or cleanly-exported pool per run).
