HOW IT WORKS (x86-64)
  address_space = a synthetic top PML4 entry -> a private PML4 page + own vma_list + mutex.
  AS0 (kernel_as) aliases the global vma_list and the arch page_table_root.
  clone_address_space(): child PML4 shares kernel slots (0, 128..511) verbatim; deep-copies app
  slots (1..127); private-writable 4K leaves -> COW in BOTH parent and child; stack + MAP_SHARED
  leaves kept shared+writable (never COW), tagged pte_shared so teardown won't free them.
  ALL live thread stacks are put in the share-range (OSv runs kernel code, incl. the irqs-off
  context switch, on the app stack, so a live stack must never be write-protected).
  thread::switch_to() loads the child CR3 only when the target AS differs (guarded).
  get_root_pt()/vm_fault resolve against the current thread's AS.  A COW write fault copies the
  page privately for the faulting side (handle_cow_write_fault).  execve() returns the thread to
  AS0 (exec discards the forked memory).  destroy_address_space() frees the child's private page
  tables + COW-copied leaves; skips shared frames and kernel slots.

DEEP-CALL-CHAIN / SAME-VA STACK  (honest status)
  The current arch/x64/fork.cc still COPIES the child stack to a NEW virtual address and biases SP.
  tst-fork-deep (NEW) forks 12 frames deep and makes the child unwind all the way up: under the
  copy+bias model the child FAULTS during the deep unwind (saved rbp/&locals point at the parent
  stack, off by the bias) -- this test DOCUMENTS the bias bug (tst-fork's shallow calls never hit it).

  I implemented the same-VA COW stack (child resumes on the parent's EXACT rsp/rbp; the child AS maps
  the parent's stack VAs to private copied pages via privatize_child_range()) and it removed the bias.
  BUT it exposed a deeper OSv issue and was REVERTED to keep the proven state:
    OSv has no separate kernel stack -- kernel code (e.g. child_exited()'s g_lock) runs on the app
    stack.  With the forking thread's stack privatized same-VA, a shared kernel mutex's wait_record
    (allocated on that stack) is at a virtual address that maps to DIFFERENT physical pages in the
    parent vs child AS.  When parent and child contend on the shared g_lock, one dereferences the
    other's wait_record through the wrong AS mapping -> lockfree::mutex::unlock() assertion.
    Root cause: kernel wait-records live on per-AS-private thread stacks.  The correct fix is to run
    the child's in-kernel lock operations on memory reachable identically in both AS (a real kernel
    stack, or keep the forking thread's stack shared and give the child a private stack the kernel
    never parks wait-records on).  This is a bounded but non-trivial follow-up; the copy+bias model
    is retained for now (shallow fork/exec/vfork/COW all correct; deep unwind is the known gap).

KNOWN GAPS (honest)
