================================================================================
ROOT CAUSE (unambiguous, from source + reproduction)
================================================================================
WHO is waiting / WHY it "hung": the guest was NOT hung on a lost inter-process
wakeup. On the ZIL-replay-at-mount path the kernel took a page fault
(handle_mmap_fault) that, depending on layout/timing, either ABORTED the guest
(single-file: "Aborted" with a zfs_mount backtrace) or corrupted enough state
that PostmasterMain wedged before "listening" (raidz1: the benchmark's
"registering ... launcher" hang). One root, two faces.

The fault (single-file backtrace, addr2line'd against libsolaris.so):
  osv::handle_mmap_fault <- mmu::vm_fault <- page_fault
  <- zfs_space              (module/os/osv/zfs/zfs_vnops_os.c:674)
  <- zfs_replay_truncate    (module/zfs/zfs_replay.c:950)
  <- zil_replay_log_record / zil_parse / zil_replay (module/zfs/zil.c)
  <- zfsvfs_setup / zfs_domount / zfs_osv_mount (module/os/osv/zfs/zfs_vfsops.c)
  <- sys_mount <- mount <- zfs_mount_at <- zfs_mount <- run_main   (AS0, no fork)

Mechanism:
  On OSv a znode loaded via zfs_zget() OUTSIDE the VFS vget() path has no
  attached vnode. zfs_znode_alloc() (module/os/osv/zfs/zfs_znode_os.c)
  kmem_zalloc's the znode and sets up the SA handle + locks but NEVER sets
  zp->z_vnode, so ZTOV(zp) == NULL. This is a KNOWN OSv-ZFS invariant, already
  guarded elsewhere (zfs_dir.c uses S_ISDIR(z_mode) instead of
  ZTOV(zp)->v_type, with a comment naming the z_vnode == NULL case).

  ZIL replay at import/mount is exactly this path. zfs_replay_truncate() does
  zfs_zget() (no vnode) then zfs_space() -> zfs_freesp() ->
  zfs_trunc()/zfs_free_range()/zfs_extend(), each of which calls
      vnode_pager_setsize(ZTOV(zp), ...)
  On OSv vnode_pager_setsize() is `static inline { vp->v_size = size; }`
  (include/osv/vnode.h:247). With ZTOV(zp) == NULL this writes NULL->v_size
  (offset ~56) -> page fault -> mount aborts before PostgreSQL runs.

  INTERMITTENT because it only fires when the ZIL has an un-synced TX_TRUNCATE
  record to replay at import (depends on export timing). This path became
  REACHABLE only when patch 0029 (commit 520a29ca) implemented zfs_space for
  ZIL replay -- before that it was an ENOTSUP stub that silently dropped the
  record, so the deref never ran.

Why the benchmark called it a "fork handoff lost wakeup": the visible last log
line on raidz1 was the postmaster's "registering background worker logical
replication launcher" (bgworker.c:980, PostmasterMain step ~928), emitted
right before CreateSharedMemoryAndSemaphores / socket-listen / recovery. The
mount-time fault (or state it corrupted) wedged the guest before "listening",
which looked like a startup handoff hang. It is the SAME root as the
single-file mount abort.

================================================================================
THE FIX  (patch 0031, module/os/osv/zfs/zfs_znode_os.c)
================================================================================
Guard each of the 3 vnode_pager_setsize() call sites (zfs_extend,
zfs_free_range, zfs_trunc) with a NULL-vnode check:

    if (ZTOV(zp) != NULL)
        vnode_pager_setsize(ZTOV(zp), ...);

Rationale: vnode_pager_setsize only updates the page-cache size hint; a
replay-loaded znode has no vnode/page cache to size, and zp->z_size + the SA
update are already authoritative. Matches the existing OSv-ZFS z_vnode==NULL
guard pattern (zfs_dir.c). NOT fork-gated -- this is a pure ZFS-on-OSv mount
bug that would also bite a non-fork OSv+ZFS build once patch 0029's zfs_space
replay is exercised. Delivered as modules/open_zfs/patches/0031-*.patch (the
OSv ZFS platform layer is maintained as working-tree patches over the
zfs-2.4.3 submodule, 0001..0031), applied in the working tree; committed to
the parent repo as 41c360da.
