================================================================================
1. THE EXACT LOST-WAKE PRIMITIVE
================================================================================
It is NOT a PG latch / self-pipe / epoll wake, and NOT a fork COW-coherence bug.
The earlier "lost self-pipe->epoll wake / f_epolls incoherence" hypothesis
(sigF-report UPDATE 3) was WRONG: the epoll_file and all its containers (map,
_activity, _activity_ring, _waiters, _activity_ring_owner) and f_epolls are
ALREADY routed to the identity kernel heap and are fully coherent cross-AS.  The
gdb "unwait_for_signal" frames on threads 405/407 were a halted-single-CPU
snapshot artifact (all showed identical this=0x1770), not a real park; and
waiters_mutex was FREE (owner=0x0).

The TRUE wedge is a virtio-blk PER-QUEUE-LOCK DEADLOCK between the block-device
submission path and its single completion thread.  From gdb on the live -smp1
wedge (loader.elf symbols):

  Thread 294 (z_wr_iss, a ZFS write-issue thread), cpu_time 5.83e9 ns, never
    returns:
      virtio::vring::add_buf_wait               drivers/virtio-vring.cc:357
      virtio::blk::make_request                 drivers/virtio-blk.cc:498
      virtio::blk_strategy ...
    make_request() holds _queue_locks[qid] (WITH_LOCK at virtio-blk.cc:402) and
    calls vring::add_buf_wait() INSIDE that lock.  The virtqueue is FULL, so
    add_buf_wait SLEEPS in wait_until(used_ring_can_gc) -- waiting for the
    completion thread to advance _used_ring_host_head (via get_buf_finalize) so
    the producer's get_buf_gc() can reclaim descriptors and make room.

  Thread 22 (virtio-blk req_done, the ONE completion thread):
      lockfree::mutex::lock                     core/lfmutex.cc:129
      virtio::blk::req_done                     drivers/virtio-blk.cc:379
    Blocked acquiring the SAME _queue_locks[q] that thread 294 holds, so it can
    run drain_queue() + wakeup_waiter().

  => Producer holds the lock and waits for the consumer; consumer needs the lock
     to run.  Classic permanent deadlock.  Disk progress = 0 forever; `select 1`
     still answers (postmaster's TCP path is independent of the blk ring); no
     crash; no self-recovery.  Exactly signature-F / F2a.

At -smp1 there is a single queue (qid = cpu_id % _num_queues = 0), fully self-
contended, so once a checkpoint's write burst saturates the ring the deadlock is
certain -- matching "~1-in-3 wedges at 'checkpoint starting: wal'".

================================================================================
2. WHICH STRUCTURE IS WRONG / ROOT CAUSE
================================================================================
Commit 1e3d8414 "virtio-blk: add multiqueue I/O support" replaced the single
`_lock` with a per-queue `std::vector<mutex> _queue_locks` AND -- the defect --
wrapped req_done()'s used-ring drain in WITH_LOCK(_queue_locks[q]).

The ORIGINAL single-queue driver (git show 1e3d8414~1:drivers/virtio-blk.cc)
held _lock across add_buf_wait() in make_request BUT drained the used ring in
req_done WITHOUT ANY LOCK.  So the completion thread always drained the ring and
woke the full-ring waiter -- no deadlock.  The multiqueue change made completions
contend on the producer's held submission lock, which is exactly the lock the
producer holds while sleeping for those completions.

The producer/consumer state is only genuinely shared on the u16
_used_ring_host_head counter: the completion side WRITES it (get_buf_finalize);
the producer READS it as the get_buf_gc() loop bound.  get_buf_gc only processes
entries the completion side has already finalized (guest_head chases host_head).
This is the lock-free producer/consumer split the original driver relied on; the
vring's own internal `_lock` member is dead/unused.

================================================================================
3. THE FIX  (drivers/virtio-blk.cc, blk::req_done -- commit f2857073)
================================================================================
Remove WITH_LOCK(_queue_locks[q]) from req_done()'s drain loop; drain +
wakeup_waiter without the per-queue submission lock, restoring the original
single-queue driver's lock-free completion path:

    for (int q = 0; q < _num_queues; q++) {
        // Do NOT take _queue_locks[q] here (see long comment): make_request
        // holds it across add_buf_wait() which sleeps for these completions;
        // taking it would deadlock.  Single-consumer drain, races get_buf_gc
        // only on the u16 _used_ring_host_head, same as upstream.
        auto* q_ring = get_virt_queue(q);
        drain_queue(q_ring);
        q_ring->wakeup_waiter();
    }

The per-queue lock still serialises concurrent make_request() producers (its
real job); it must not gate completions.  The drain is single-consumer (only the
one req_done thread runs it).  Not #if CONF_fork -- this is generic virtio-blk
correctness (the deadlock exists in any multiqueue OSv build), but it is only
reached under fork+ZFS+PG heavy write load, so it is behaviourally fork-gated and
a no-op for anything that does not saturate a virtqueue.  The change adds/removes
no fork macros, so conf_fork=0 compiles byte-for-byte the same logic.

================================================================================
4. CLASSIFICATION
================================================================================
signature-F was three faces of "resuming/serving a busy forked PG under heavy
ZFS write load":
  F1  (FIXED, 1ae2602f): FPU control-word reload after the CR3 swap in switch_to
      -> ldmxcsr #GP on resume of a COW fork child.
  F2a (FIXED, f2857073, THIS): virtio-blk req_done per-queue-lock deadlock ->
      permanent full-ring completion stall = the pure -smp1 lost-wakeup wedge.
  F2b (NOT fixed, out of scope): -smp>1 scheduler-migration bstree "insert_before
      node unique" runqueue double-insert.  Still crashes a subset at -smp>1.
Separately, an EIO read/write-path corruptor facet remains (crashes a subset at
both -smp1 and -smp4); distinct from F2a (a crash, not a wedge).
