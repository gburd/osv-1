WHAT signature-F IS (reproduced, this base)
================================================================================
Heavy load (pgbench -i -s1000 COPY, or -c16 -T120) intermittently (~1 in 3-4
runs, -smp4 KVM) WEDGES at "checkpoint starting: wal": guest ~idle, disk grow=0,
pgbench -i dies with "PQputline failed" (server COPY backend stopped reading).
The postmaster + a fresh `select 1` STILL ANSWER -> not a total hang.  0
corruptor signatures (no VERIFY/range_tree/EIO wild write).  A re-run completes.

Reproduced on PRISTINE 6ccf4a92 with the ORIGINAL heavy-repro.sh (no gdb stub):
run wedged CLEAN at "checkpoint starting: wal", pgbench -i rc=1 (PQputline),
NO crash signature.  So this is a real base defect, not a harness artifact.

WHO IS PARKED (gdb on the wedged guest, loader.elf symbols):
  588 postmaster    epoll_file::wait           (ServerLoop -> answers select 1)
  590 CHECKPOINTER  epoll_wait on its latch    (the wedge: "starting", no "complete")
  595 a COPY/backend sys_read -> pipe_buffer::read
  591/594/598       parked backends (switch_to, COW stacks)
The checkpointer (590) is a fork child of 588, status=waiting, cleanly parked on
its latch's epoll self-pipe, NOT on a runqueue, stack pages present.

It is a FORK WAKE/SCHEDULE-COHERENCE bug in OSv's scheduler switch/resume of a
COW fork child, with THREE observed faces (all the same root -- resuming/ waking
a fork child whose per-AS context is not coherently present):
  (a) CLEAN STALL: the wake silently fails to schedule the child -> it never
      runs -> the checkpoint never completes.  (release / no-assert path)
  (b) ldmxcsr #GP in switch_to        == F1 (FIXED below)
  (c) assert(sched::preemptable()) page_fault (COW page absent in incoming AS
      during the non-preemptable switch) / boost::intrusive bstree insert_before
      "node unique" (runqueue double-insert) == F2 (open)
Instrumentation proved the SIGURG delivery itself is 100% reliable:
  kill_urg_child=47 urg_dispatched=47 urg_sigdfl=0 kill_urg_noas=0
  wake_epoll_call=22506 deliver=22390 noep=77
So it is NOT a lost signal / lost self-pipe write; it is the SCHEDULER RESUME of
the woken fork child that is unsafe.

================================================================================
F1 -- FPU control-word reload after the CR3 swap  (FIXED, commit 1ae2602f)
================================================================================
switch_to()'s #1020 FPU-reset tail did:
    auto fpucw = fnstcw(); auto mxcsr = stmxcsr();   // spilled to -0x34(%rbp)..
    <switch_as asm: swap rsp/rbp, load incoming CR3, jmp>
    emms; fldcw(fpucw); ldmxcsr(mxcsr);              // read -0x42/-0x48(%rbp)
The compiler stores fpucw/mxcsr in %rbp-relative stack slots.  In the CONF_fork
switch_as path the asm swaps rsp/rbp AND CR3 to the incoming fork child FIRST,
so fldcw/ldmxcsr read the incoming child's stack under the incoming COW AS --
garbage.  gdb proof on the wedged guest: poking the checkpointer -> #GP at
switch_to+251 (ldmxcsr), RSP/RBP == the checkpointer's; the saved slot held
0xbffc8ea8 (low half of a heap pointer) -> reserved MXCSR bits -> #GP -> the
resumed thread dies -> permanent wedge.

FIX (arch/x64/arch-switch.hh, #if CONF_fork switch_as branch): restore the
canonical control words (0x37f / 0x1f80 -- what every OSv thread uses; switch_to
does no fxsave/fxrstor so no per-thread FPU data is preserved anyway) from a
kernel-IDENTITY-MAPPED static.  fldcw/ldmxcsr address that fixed .rodata slot
(RIP-relative), so the reload neither READS the incoming child's garbage stack
(#GP) nor WRITES it (a COW write-fault in the non-preemptable switch ->
assert(preemptable()) abort).  Non-fork path byte-identical.  Verified in the
built loader: `fldcw 0x..(%rip) # canon_fpucw`, `ldmxcsr 0x..(%rip) # canon_mxcsr`.

F2 -- COW page absent in the incoming AS during the non-preemptable switch (OPEN)
================================================================================
After F1, heavy load STILL intermittently wedges/asserts.  gdb: waking a parked
fork child -> page_fault at a COW address while !preemptable():
    assert(sched::preemptable())  (arch/x64/mmu.cc:38)  -> abort
faulting cr2 seen: a COW same-VA STACK addr (0x2000002002xx) and a fork-arena
addr (0x30000..); also boost bstree insert_before (runqueue node double-insert).
Root: switch_to / the scheduler resume touches a page (incoming child's COW
stack, or a per-CPU/timer/runqueue structure) that is NOT PRESENT in the
incoming child's address space, and the fault lands inside the non-preemptable
switch where vm_fault (which may sleep) is illegal.  In release (no assert) the
same missing-page / racy enqueue silently corrupts the runqueue / drops the
wake -> the CLEAN STALL.

F2 FIX DIRECTION (mirror F1: the resume must touch NOTHING that needs a COW
fault under the incoming AS in the non-preemptable window):
  (a) pre-fault / pin the fork child's kernel+app stack pages into ITS AS at
      child creation / first schedule, so resume never COW-faults the stack; or
  (b) ensure switch_to + the post-switch unpark_timers/enqueue path touch only
      shared-identity or already-present pages during the non-preemptable window.
Pick the minimal correct one, #if CONF_fork.

UPDATE 3 -- F2a PINNED: infinite-timeout latch wait + lost self-pipe->epoll wake
================================================================================
On the -smp1 TRUE wedge, the checkpointer (407) has _active_timers EMPTY
(size_=0), _timers_parked=false.  So it is blocked in epoll_wait with NO
timeout timer -> an INFINITE-timeout WaitLatch (PG's ConditionVariableSleep /
WaitLatch(..., timeout=-1) path uses no WL_TIMEOUT).  With no timeout, a lost
latch wake is a PERMANENT wedge -- exactly what we see (420s+, never recovers).
This is why it is permanent, not a 300s-timeout recovery.

The wake that is lost: SetLatch(child) -> kill(child,SIGURG) -> OSv spawns the
handler thread (PROVEN reliable: kill_urg_child==urg_dispatched) -> in the
child's AS latch_sigurg_handler -> sendSelfPipeByte writes the child's
selfpipe_writefd -> the pipe read-end poll_wake -> file::wake_epoll walks the
fd's f_epolls -> epoll wake.  Instrumentation caught f_epolls EMPTY on
sigF_wake_epoll_noep=77 poll_wakes: SOME poll_wakes found NO epoll registered on
the fd.  PRIME F2a HYPOTHESIS: a fork child's epoll_ctl(ADD, selfpipe_readfd)
registration in the file's f_epolls is lost / incoherent across the fork, so the
self-pipe write's poll_wake finds no epoll to wake -> the latch byte is written
but the child's epoll_wait is never notified -> lost wake -> (with the infinite
timeout) permanent wedge.  The wait_record itself IS already coherent
(wait_object<waitqueue> uses coherent_wait_record); the gap is the fd->epoll
readiness-notify registration (f_epolls) coherence for a forked backend's
self-pipe.

F2a NEXT STEP (handoff, highest value): verify the wedged child's
selfpipe_readfd file has THIS child's epoll in its f_epolls (read gfdt[selfpipe
_readfd]->f_epolls); if empty/stale -> fix f_epolls registration to be coherent
for fork children (like the wait_record/coherent_wait_record fix), so
poll_wake->wake_epoll reliably reaches the forked backend's epoll.  That closes
the lost self-pipe->epoll wake.  Then re-run the -smp1 420s test + the 10x
qualify.  (F2b -- the -smp>1 migration bstree double-insert -- is a separate,
SMP-only scheduler race.)
