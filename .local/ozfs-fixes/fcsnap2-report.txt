    FIRST  warm launch (restore snapshot-A)         restore->first query = 0.176 s
    SECOND warm launch (restore FROZEN snapshot-B)  restore->first query = 0.174 s (round1)

TASK 1(A): RNG-on-resume  --  CONFIRMED REAL BUG, FIXED, VALIDATED
--------------------------------------------------------------------------------
  New master PR branch:  pr/rng-reseed-on-resume   (cut on upstream/master cb8c7205b)
  Bundle: /tmp/fix-rng.bundle  (git bundle create ... cb8c7205b..pr/rng-reseed-on-resume)
  Author: Greg Burd <greg@burd.me>.  No em-dashes.  Conf-gated (default on).
  Files:  drivers/random.cc, drivers/random.hh, drivers/kvmclock.cc, conf/kconfig/core

  HOW THE GAP WAS PROVEN (dedicated in-guest probe, not the weak PG-only probe):
    Built a minimal rofs OSv image (upstream/master) with a probe app that reads
    N=32 bytes from /dev/urandom, /dev/random, and getrandom() in a loop. Booted
    it, took a Full snapshot mid-run, then restored the SAME snapshot into TWO
    separate Firecracker processes and compared the first post-resume bytes.

    On this host (m5d.metal HAS RDRAND + RDSEED), OSv's Yarrow CSPRNG is
    continuously reseeded from RDRAND by the ~100 ms harvest thread, so the two
    clones DIVERGE on every source even on the first post-resume read. No bug
    observed WHEN a live hardware entropy source exists.

    To test the real risk (a host with NO RDRAND and NO virtio-rng, e.g. many
    ARM/AMD/restricted guests, or any guest Firecracker does not give an entropy
    device), RDRAND source registration was disabled in a test build. Result,
    two clones from the SAME snapshot, EVERY post-resume read:

      clone1 urandom = 9c37f17fa3331cabc84f7adece7ee088e2bd61d9167a91022ddecd1476c805b0
      clone2 urandom = 9c37f17fa3331cabc84f7adece7ee088e2bd61d9167a91022ddecd1476c805b0
      -> IDENTICAL (SHARED OS RNG STATE)   [3 of 3 reads identical]

    That is a real correctness and security bug: a cloned fleet would share
    session keys, TCP ISNs, UUIDs, etc. A full-VM snapshot captures the entire
    entropy pool + CSPRNG state, and with no live source nothing ever remixes it.

  THE FIX:
    On hypervisor resume, force the CSPRNG to re-key, mixing in material that is
    guaranteed to differ between two clones EVEN WITH NO hardware entropy source:
    the wall-clock instant the hypervisor handed us on resume (each clone resumes
    at a distinct host wall-clock time) plus the resume-time TSC. The unique
    material is fed into the harvest queue and an explicit reseed is commanded.

    Resume detection (no OSv resume hook exists, so this is passive): on
    Firecracker the guest system clock keeps advancing during the pause (the TSC
    runs through the pause), so a resume shows up as a large forward jump in
    system_time. TWO detectors, both gated by CONF_core_reseed_on_resume:
      1. The existing 1 Hz kvmclock wall-clock sync thread notices its 1 s sleep
         apparently took much longer (> 1.5 s) and reseeds. Latency <= ~1 s.
      2. The /dev/random read path notices the gap since the previous read
         (> 0.5 s) and reseeds before serving, closing the sub-second window so
         even the FIRST post-resume read diverges.

  VALIDATION (rebuilt with the fix):
    - Fix + RDRAND DISABLED (worst case): two clones now DIFFER on the FIRST
      post-resume read (3 of 3 reads differ). Bug fixed.
    - Fix + RDRAND ENABLED (normal host): clones DIFFER, normal boot unaffected,
      /dev/random works. Strict improvement, no regression.
    - Behavior gate: only runs when a resume is actually detected, so a
      never-resumed or freshly-booted guest follows the same path as before;
      CONF_core_reseed_on_resume=0 removes it entirely.

TASK 1(B): kvmclock-resync-on-resume  --  NOT NEEDED (gap not real on Firecracker)
--------------------------------------------------------------------------------
  No PR. Reporting honestly instead of inventing a fix.

  The prior report noted a +50-85 ms "ahead" offset on resume. A dedicated,
  clean in-guest measurement shows that was a host-side measurement artifact
  (log flush + guest scheduling latency), not a real guest clock error.

  METHOD: a probe prints CLOCK_REALTIME; a Full snapshot is taken; on restore
  the guest's first post-resume realtime is compared against the host wall clock
  at the exact resume-API-return instant (T1 recorded by the FC driver).

  RESULT, stock upstream/master kvmclock under Firecracker, 5 restores:
    run 1: offset (guest - host) = +0.000667 s
    run 2:                         +0.000655 s
    run 3:                         +0.000632 s
    run 4:                         +0.000630 s
    run 5:                         +0.000612 s
  Stable +0.6-0.7 ms, which is essentially the measurement floor (the guest
  scheduling + printing its first read). No 50-85 ms offset.

  CORROBORATION: instrumenting the kvmclock wall-clock sync thread to flag any
  jump > 2 ms in wall_clock_boot across a resume fired NOTHING across many
  restores. And CLOCK_MONOTONIC advanced smoothly through the pause (no backward
  jump, no timer storm, no hang). Firecracker lets the guest TSC run through the
  pause, so kvmclock's TSC interpolation keeps realtime tracking the host to
  sub-millisecond immediately on resume.

  Conclusion: on Firecracker + OSv master, the resumed clock is already correct
  to sub-ms with no fix. If a different hypervisor (or FC configured to freeze
  the TSC) ever produced a real offset, the minimal fix would be to force an
  immediate sync_wall_clock() on the first tick after a detected discontinuity;
  that machinery already exists (the RNG fix reuses the same resume detector),
  but it is a no-op here because there is no discontinuity to correct.
