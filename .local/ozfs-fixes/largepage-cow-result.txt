--------------------------------------------------------------------------------
THE REAL ROOT CAUSE (the ticket's diagnosis was PARTIALLY WRONG)
--------------------------------------------------------------------------------
The ticket said: "OSv backs the malloc heap with 2 MB huge pages ... clone
shares them verbatim ... fix clone_pt_level<1>/handle_cow_write_fault."

I fixed exactly that (large-page COW) and PROVED it works for large allocations
(BIG heap isolated).  But it does NOT fix PostgreSQL, because PG's crashing
heap state is in the SMALL-object heap, and the small-object heap does NOT live
in an application-slot large page.  Measured (VA slot = addr >> 39):

    small malloc  ->  0x600000...   PML4 slot 192   = mem_area::mempool
    large malloc  ->  0x200000...   PML4 slot 64    = application mmap area (COW-able)
    MAP_SHARED    ->  0x200000...   PML4 slot 64
    .data/.bss    ->  0x100000...   slot 32         (COW-able)

OSv's PML4 layout (core/mmu.cc:142):
    slots 1..127   : application VMA space  -- PRIVATE, cloned per child (COW)
    slots 128..511 : kernel identity / phys / mempool / debug maps -- SHARED

Small-object malloc returns pointers in the mem_area::mempool identity map
(slot 192, base 0x420000000000... actually 0x600... = 3<<43 within the mempool
band).  clone_address_space() shares slots 128..511 VERBATIM as "kernel" (this
is BY DESIGN -- OSv has no user/kernel split and the kernel heap must stay
coherent across address spaces; see commit a0e9fd81's message: "Kernel PML4
entries are shared ... so OSv code + the kernel heap work identically").

So PG's per-backend small-object heap (MemoryContexts, catcache/relcache,
GUC tables, cached pointers) is silently SHARED between parent and every forked
child, gets corrupted, and the next child NULL-derefs.  The large-page COW fix
never even sees this memory -- it is not in slots 1..127.

Additionally: virt_to_phys() on identity-mapped (slots 128..511) addresses is
pure ARITHMETIC (addr & mask), not a page-table walk.  So the heap CANNOT be
made COW in place -- giving a child a different physical page at the same
identity VA would break virt_to_phys() for that page (used by the kernel, e.g.
for DMA on the I/O path).  COW-ing the identity map is architecturally
impossible without breaking the kernel.

--------------------------------------------------------------------------------
WHAT IT WOULD TAKE (and what I prototyped)
--------------------------------------------------------------------------------
Correctly isolating the small-object heap requires MOVING the application heap
out of the shared kernel identity map into a page-table-mapped, COW-able
application-slot region (so both per-AS COW AND page-walk virt_to_phys work).

I prototyped this as a "fork heap arena": a fixed application-slot mmap region
(PML4 slot 120) that backs the malloc pools under CONF_fork, with free()/
object_size() taught to recognise arena VAs, and the arena eagerly PRIVATISED
(byte-copied, plain-writable, NO COW) at fork -- privatise rather than COW is
mandatory because the KERNEL writes heap objects with preemption/irqs off
(inside preempt_lock in the allocator, on the I/O path), where a COW write
fault is illegal (asserts sched::preemptable()).

Status of that prototype (NOT committed -- it is not shippable yet):
  - It DID move the small heap into a COW-able app slot (verified: heap moved
    from slot 192 to slot 120, boot succeeds, "parent:" prints).
  - It resolved several sub-issues along the way: the arena's own free-back to
    the identity page allocator (guarded), the arena reservation colliding with
    the mmap region / thread stacks / shmem (moved to a dedicated fixed slot),
    the arena's demand-paged pages faulting under preempt_lock (pre-touch),
    and clone_address_space's own bookkeeping allocating from the very arena it
    was cloning (per-thread bypass to the identity heap).
  - BUT it still hits a fork-time RECURSIVE fault ("exception nested too
    deeply") on the child's resume/teardown path that I could not root-cause in
    the time available.  The recursion is pre-vm_fault (fault-on-fault, likely
    on the exception/stack path), and it persists even with the child doing
    nothing but _exit(42) and even with the arena privatise disabled -- i.e. it
    is triggered by merely routing the heap through the arena, independent of
    the privatise copy.  This needs deeper work across the allocator, the fault
    path, the fork trampoline (arch/x64/fork.cc), and __osv_run_atfork_child.

I deliberately did NOT commit the arena: a half-working heap allocator that
crashes fork is worse than the proven, contained large-page fix plus an honest
diagnosis.  Committing it would violate "replicate the WHOLE mechanism
correctly" -- it is a partial mechanism.
