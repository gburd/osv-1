4. IS ANYTHING IN 2.4.3 OSv-RELEVANT?  (skim of zfs-2.4.2..zfs-2.4.3)
--------------------------------------------------------------------------------
2.4.3 is a small patch release; the large majority of commits are CI, FreeBSD,
and Linux-kernel-compat changes that OSv does not compile (OSv has its own
platform layer). None conflicted with our series (all 29 applied clean). The
commits that DO touch shared module/zfs core sources OSv compiles, worth noting:

  8dd2e0096  enforce exact decompressed length for lz4/gzip/zstd
             -> data-integrity hardening on the decompression path OSv uses
                (gzip.c, lz4_zfs.c, zstd/zfs_zstd.c). Good to inherit.
  137626695  arc: export additional required symbols (arc.c)
             -> symbol export; OSv links these into libsolaris.so. Built clean.
  8e964b36b  key lookup failure should always return EACCES (dsl_crypt.c, arc.c)
             -> encryption path; relevant to OSv patch 0008 (AES-256-GCM). Our
                patch touches different lines; applied + compiled clean.
  06d8cfedb  additional verification of size fields and strings (dmu_recv.c,
             vdev_label.c, zfs_ioctl.c, zfs_quota.c)  -> send/recv + ioctl
                robustness.
  63a0ff6cd  nvpair: check for un-terminated strings in packed nvlist
             (nvpair.c, zfs_ioctl.c)  -> ioctl input hardening.
  6d336fa86  abd: fix stats asymmetry in case of Direct I/O (abd.c)
             -> ARC/ABD stats; near OSv patches 0009/0019 territory but
                different lines; clean.
  Others (dbuf prefetch/l2cache simplify, zil.c uninit-var + log-vdev-removal
  fix, dsl_scan errorscrub cursor, sa lock-ordering, dsl_dir dd_lock annotate,
  dmu_send off-by-one redaction fix, zvol block-clone key check) also compiled
  into OSv's libsolaris.so cleanly.

  Bottom line: no OSv-specific behavior change is required by 2.4.3; OSv simply
  inherits upstream's decompression-length, nvlist/size-field, and encryption
  error-code hardening for free. Nothing regressed our patch series.
