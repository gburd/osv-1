=== GOAL 2: the plateau bottleneck, NAMED with evidence (profiled under RO c32) ===
EVIDENCE 1 (host CPU accounting): during RO c32 the qemu process (48-vCPU guest) uses ~206-246% of 4800%
  = ~2-2.5 of 48 vCPUs busy; host reports 97% IDLE. If OSv were scaling across 32 connections it would use
  ~32 cores. It uses ~2.5. => plateau is NOT CPU-bound, NOT storage-bound.
EVIDENCE 2 (per-vCPU-thread top -H of qemu): only 6-7 vCPU threads >5% CPU (2 pegged at 100%, then a sharp
  taper 86/66/60/40%); the other ~42 vCPU threads at 0.0% (idle).
EVIDENCE 3 (gdb `osv info threads`, 1379 threads, under RO c32):
  - virtio-net-rx threads = 1  (a SINGLE receiver thread, id 254, PINNED on cpu1, blocked in
    virtio_driver::wait_for_queue at drivers/virtio.cc:159)
  - virtio-tx-* threads   = 48 (one TX per vCPU - TX is per-CPU, RX is NOT)
  - netisr threads        = 1
  - 41 PG backends cluster on just 5 CPUs: cpu1=15, cpu0=11, cpu2=10, cpu3=4, cpu4=1  (43 vCPUs never used)
  - backend states: 36 waiting (in sched::thread::switch_to, i.e. blocked awaiting wakeup), 3 running, 2 queued

NAMED SERIALIZED RESOURCE: the SINGLE virtio-net RX receiver thread + wake-to-waker-CPU scheduler placement.
  All inbound pgbench packets funnel through ONE rx thread on cpu1. It wakes the target backend; OSv has NO
  wake-time idle-CPU steering (thread::wake_impl re-queues a woken thread onto its last/home CPU, and the
  only rebalancer is a lazy 100ms/1-thread load_balance), so every woken backend lands on/near the waker's
  CPU. Work packs onto ~5 CPUs adjacent to the single RX thread; 43 vCPUs idle. Aggregate throughput is capped
  by what ~2-3 CPUs can push through the single-RX + wake-round-trip path, independent of vCPU count - exactly
  a flat-but-low plateau. This CONFIRMS (does not refute) the prior "RX-receiver-placement / wake-round-trip
  latency residual" hypothesis, now with direct thread-placement + single-RX-thread + idle-CPU evidence.

CONCRETE NEXT WORK (the one lever, higher-leverage first):
  (1) WAKE-TIME IDLE-CPU STEERING in core/sched.cc thread::wake_impl: when waking an unpinned thread whose
      home CPU is loaded and an idle CPU exists, place it on the idle CPU (a Linux select_task_rq analog).
      This is the OS-general, highest-leverage fix - it directly disperses the backend clump the single RX
      thread creates, letting the 43 idle vCPUs absorb work. (Prior #1464 shortened load_balance but did NOT
      add wake-placement; the clump persists - proven here.)
  (2) MULTI-QUEUE RX with per-queue receiver threads pinned across CPUs (spread the single RX). #1463 MQ ALONE
      did NOT help in prior A/Bs precisely because it doesn't fix wake placement - woken backends still return
      to their clumped home CPU. (1) and (2) are complementary; (1) is the prerequisite that makes (2) pay off.
  => Recommendation: implement (1) wake-time idle-CPU steering FIRST; re-measure the RO curve; then add (2) MQ.
