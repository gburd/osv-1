OPEN DESIGN QUESTION (flag for human, do NOT auto-post): nyh asked whether the
kvmclock.cc resume detector is now REDUNDANT given random.cc detects the clone
immediately on the first read after resume. Drafted reply below.

DRAFT REPLY (1461, needs human review before posting):
"""
Good question. The two detectors cover different windows and I would keep both:

- The random.cc read-path detector (reseed_if_resumed) fires immediately, but
  ONLY on the first /dev/random / getrandom() read after resume. A clone that is
  resumed and does something security-relevant that does NOT first read the OS
  RNG (e.g. reuses an in-memory session key, or emits a TCP ISN from cached
  state) would not be covered by it alone.
- The kvmclock.cc 1Hz sync-thread detector fires within ~1.5s of resume even if
  the guest never reads the RNG, so it closes that no-read window.

So they are complementary: the read-path one removes the up-to-1.5s latency for
the common case (something reads the RNG right away), and the kvmclock one
guarantees a reseed happens regardless of whether anything reads. Removing the
kvmclock detector would reopen the "resumed clone that never reads the RNG"
gap. I documented this cross-reference in both files. Happy to drop it if you
would rather rely solely on the read path, but I think the belt-and-suspenders
is worth the few lines here. (The proper long-term fix for both is VMGENID, noted
as the future enhancement.)
"""
