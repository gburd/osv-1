# x86 silent wedge under TPROC-C load: a NEW bug, not the one we fixed

2026-09-08, agent d4454474, during the first x86 sweep that ever reached a timed window.

## Evidence that it is new
- guest wedged at 21:05:51 UTC; last console line is a **`checkpoint starting: time` that never
  completed**
- TCP :5432 **still accepts**, but no query ever returns (psql times out at 25-30 s)
- device **0.00% util** (fully idle)
- qemu **50% of one core** (of a 3200% ceiling)
- **ZERO page faults**, and no OOM / abort / assert / panic in **68,751 console lines**

**Zero page faults across the entire run is the decisive datum**: the elf/dlopen fix validated in
Task A is NOT implicated, and its own gate held all run. This is a silent hang with a stuck
checkpoint on an idle device - a different failure, plausibly the same family as the
"unattributed stall" seen at VU32 (see BOTTLENECK-THREE-ANSWERS.md).

## Data accounting (reported as-is, not smoothed)
Valid, healthy-guest cells: **VU8 x3, VU16 x3, VU32 x3, VU64-r1** = 10 cells.
- VU8 43,407 (spread 5.9%), VU16 37,690 (6.3%), VU32 34,789 (0.8%) - peak at VU8, monotonic
  decline, same shape as the Linux reference.
- **VU64-r1 kept as valid**: it completed with 26,874 NOPM and **0 connection errors**, even though
  the console had already died during its window. Reported with that caveat so a reader can judge,
  rather than silently dropped.
- Everything after the wedge marked **failed, not slow** ("could not receive data from server"), so
  nobody later reads it as a throughput collapse.

## Asked for, if cheap
A gdb attach to the qemu process and `thread apply all bt`, to learn **what the checkpointer and
the idle threads are blocked on**. One backtrace would likely name the bug. Told not to spend long
if the guest is truly unresponsive.

## Firecracker: not reached, and that is the right call
Out of budget once two bugs were characterised. "Not reached" beats a rushed second hypervisor,
and the earlier campaign already established Firecracker is not exempt from guest-kernel bugs, so
its open question is throughput parity rather than correctness.
